# 03-数据库设计

## 概述

本系统使用 **MySQL** 作为数据库，通过 **GORM** 进行 ORM 映射。所有业务表默认继承 GVA 框架的 `GVA_MODEL` 基础结构（ID、CreatedAt、UpdatedAt、DeletedAt），实现统一的软删除与时间戳管理。

### ER 关系总览

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ goods_category│    │    brand     │    │   supplier   │
└──────┬───────┘    └──────┬───────┘    └──────┬───────┘
       │                   │                   │
       └───────────────────┼───────────────────┘
                           │
                    ┌──────▼──────┐
                    │    goods    │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐    ┌──────────────┐
                    │  goods_sku  │◄───│    stock     │──► warehouse
                    └──────┬──────┘    └──────┬───────┘
                           │                  │
              ┌────────────┼──────────┐       │
              │            │          │       │
       ┌──────▼──────┐ ┌───▼────┐ ┌───▼────┐   │
       │purchase_item│ │sale_item│ │check   │   │
       └──────┬──────┘ └───┬────┘ │_item   │   │
              │            │      └────────┘   │
       ┌──────▼──────┐ ┌───▼────┐              │
       │purchase_    │ │sale_   │              │
       │order        │ │order   │              │
       └─────────────┘ └────────┘              │
                                      ┌────────▼──────┐
                                      │  stock_log    │
                                      └───────────────┘
```

### 通用约定

| 约定项 | 说明 |
|--------|------|
| 主键 | 统一使用 `id BIGINT UNSIGNED AUTO_INCREMENT` |
| 时间戳 | 继承 GVA_MODEL：`created_at`、`updated_at`、`deleted_at`（软删除） |
| 金额字段 | 统一使用 `DECIMAL(12,2)`，避免浮点精度问题 |
| 数量字段 | 使用 `INT`，默认值 0 |
| 状态字段 | 使用 `TINYINT`，具体枚举值各表定义 |
| 编码字段 | 使用 `VARCHAR(50)`，加唯一索引 |
| 表名 | 全部小写，下划线分隔（snake_case） |
| 引擎 | InnoDB（支持事务） |
| 字符集 | utf8mb4 |

## 一、基础资料

基础资料是系统的数据字典，被商品、采购、销售等核心模块引用。

### 1. 商品分类（goods_category）

**表用途**：管理商品的多级分类树（如：女装 > 上衣 > T恤），支持无限层级嵌套。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| parent_id | BIGINT UNSIGNED | NULL | NULL | 父分类ID，NULL 表示根节点 |
| code | VARCHAR(50) | NOT NULL | - | 分类编码，全局唯一 |
| name | VARCHAR(100) | NOT NULL | - | 分类名称 |
| sort | INT | NOT NULL | 0 | 排序值，越小越靠前 |
| status | TINYINT | NOT NULL | 1 | 状态：1=启用，0=停用 |
| remark | VARCHAR(500) | NULL | NULL | 备注 |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间 |
| updated_at | DATETIME(3) | NOT NULL | - | 更新时间 |
| deleted_at | DATETIME(3) | NULL | NULL | 删除时间（软删除） |

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_code | 唯一索引 | code | 编码全局唯一 |
| idx_parent_id | 普通索引 | parent_id | 查询子分类 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| parent_id | goods_category | id | 自引用，父分类 |

**业务规则**：
- 删除前检查是否被商品（goods）引用，若有引用则禁止删除
- 删除父分类时，子分类的 `parent_id` 变为 NULL（SET NULL），或同样禁止删除（建议后者更安全）
- `code` 不可修改，创建后即固定

**使用示例**：
```sql
-- 查询所有一级分类
SELECT * FROM goods_category WHERE parent_id IS NULL AND deleted_at IS NULL ORDER BY sort;

-- 查询某分类下的所有子分类
SELECT * FROM goods_category WHERE parent_id = 1 AND deleted_at IS NULL ORDER BY sort;

-- 递归查询分类树（MySQL 8.0+ CTE）
WITH RECURSIVE cte AS (
    SELECT * FROM goods_category WHERE id = 1
    UNION ALL
    SELECT gc.* FROM goods_category gc INNER JOIN cte ON gc.parent_id = cte.id
) SELECT * FROM cte WHERE deleted_at IS NULL;
```

**为什么这样设计**：
- **parent_id 自引用**：服装行业分类层级深（女装→上衣→T恤→短袖T恤），自引用方案简单通用，无需额外闭包表；个体户场景层级有限（通常 2-3 层），CTE 递归查询足够
- **code 唯一**：编码作为业务标识，比名称更稳定，可用于前端路由参数
- **sort 字段**：允许用户自定义分类展示顺序，比按名称字母排序更灵活

### 2. 品牌（brand）

**表用途**：管理服装品牌信息（如 Nike、Adidas、无品牌等）。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| code | VARCHAR(50) | NOT NULL | - | 品牌编码，全局唯一 |
| name | VARCHAR(100) | NOT NULL | - | 品牌名称 |
| logo | VARCHAR(500) | NULL | NULL | 品牌 logo 图片 URL |
| status | TINYINT | NOT NULL | 1 | 状态：1=启用，0=停用 |
| remark | VARCHAR(500) | NULL | NULL | 备注 |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间 |
| updated_at | DATETIME(3) | NOT NULL | - | 更新时间 |
| deleted_at | DATETIME(3) | NULL | NULL | 删除时间（软删除） |

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_code | 唯一索引 | code | 编码全局唯一 |
| idx_name | 普通索引 | name | 按名称搜索 |

**外键关系**：无（被 goods 引用）

**业务规则**：
- 删除前检查是否被商品引用，若有引用则禁止删除
- `code` 不可修改

**使用示例**：
```sql
-- 模糊搜索品牌
SELECT * FROM brand WHERE name LIKE '%耐克%' AND status = 1 AND deleted_at IS NULL;
```

**为什么这样设计**：
- **独立品牌表**：服装行业品牌是重要筛选维度，独立管理方便维护和统计；个体户可能按品牌进货和销售，品牌维度在报表中有实际价值
- **logo 可为空**：个体户场景中品牌 logo 非必需，降低使用门槛

- **独立编码**：方便与原供应商台账对账

## 二、商品中心

商品中心是进销存的核心，采用 **SPU + SKU** 两级模型：
- **SPU（goods）**：标准化产品单元，描述一个商品的基本属性
- **SKU（goods_sku）**：库存量单位，描述具体可售卖的最小单元（颜色+尺码组合）

### 1. 商品 SPU（goods）

**表用途**：管理商品的基本信息，一个商品对应多个 SKU。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| code | VARCHAR(50) | NOT NULL | - | 商品编码（款号），全局唯一 |
| name | VARCHAR(200) | NOT NULL | - | 商品名称 |
| category_id | BIGINT UNSIGNED | NULL | NULL | 分类ID |
| brand_id | BIGINT UNSIGNED | NULL | NULL | 品牌ID |
| unit | VARCHAR(20) | NOT NULL | '件' | 计量单位（件、条、双等） |
| image | VARCHAR(500) | NULL | NULL | 商品主图 URL |
| status | TINYINT | NOT NULL | 1 | 状态：1=上架，0=下架 |
| remark | VARCHAR(500) | NULL | NULL | 备注 |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间 |
| updated_at | DATETIME(3) | NOT NULL | - | 更新时间 |
| deleted_at | DATETIME(3) | NULL | NULL | 删除时间（软删除） |

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_code | 唯一索引 | code | 款号唯一 |
| idx_category_id | 普通索引 | category_id | 按分类筛选 |
| idx_brand_id | 普通索引 | brand_id | 按品牌筛选 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| category_id | goods_category | id | 所属分类 |
| brand_id | brand | id | 所属品牌 |

**业务规则**：
- 删除前检查是否存在关联 SKU，若有则禁止删除
- 删除前检查是否存在库存，若有则禁止删除
- 删除前检查是否存在采购/销售记录，若有则禁止删除
- `code` 作为款号不可修改
- 分类和品牌可设为 NULL（允许"未分类"/"无品牌"）

**使用示例**：
```sql
-- 按分类查询商品（含品牌名）
SELECT g.*, gc.name AS category_name, b.name AS brand_name
FROM goods g
LEFT JOIN goods_category gc ON g.category_id = gc.id
LEFT JOIN brand b ON g.brand_id = b.id
WHERE g.category_id = 1 AND g.deleted_at IS NULL;
```

**为什么这样设计**：
- **SPU+SKU 分离**：服装行业典型模式 — 一个款号（SPU）下有多个颜色×尺码组合（SKU），分离后 SPU 层管理公共属性，SKU 层管理库存和价格
- **unit 字段**：服装行业单位不统一（件/条/双/套），独立字段比硬编码更灵活
- **image 单图**：v1 阶段用单张主图，后续可扩展为 `goods_image` 多图表
- **原字段名 `uint` 修正为 `unit`**：`uint` 是 Go 关键字也是无符号整数类型名，容易混淆

---

### 2. SKU（goods_sku）

**表用途**：管理商品的具体规格（颜色+尺码组合），是库存和交易的最小单位。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| goods_id | BIGINT UNSIGNED | NOT NULL | - | 所属商品ID |
| sku_code | VARCHAR(50) | NOT NULL | - | SKU 编码（商品编码+颜色+尺码组合），全局唯一 |
| barcode | VARCHAR(50) | NULL | NULL | 条码（可为空，支持无条码场景） |
| color | VARCHAR(50) | NOT NULL | - | 颜色（如：红色、黑色） |
| size | VARCHAR(50) | NOT NULL | - | 尺码（如：S、M、L、XL） |
| cost_price | DECIMAL(12,2) | NOT NULL | 0.00 | 成本价（采购进价） |
| sale_price | DECIMAL(12,2) | NOT NULL | 0.00 | 销售价（吊牌价/零售价） |
| status | TINYINT | NOT NULL | 1 | 状态：1=启用，0=停用 |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间 |
| updated_at | DATETIME(3) | NOT NULL | - | 更新时间 |
| deleted_at | DATETIME(3) | NULL | NULL | 删除时间（软删除） |

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_sku_code | 唯一索引 | sku_code | SKU 编码全局唯一 |
| idx_goods_id | 普通索引 | goods_id | 按商品查 SKU |
| idx_barcode | 普通索引 | barcode | 按条码检索 |
| idx_color_size | 普通索引 | (color, size) | 按颜色+尺码组合筛选 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| goods_id | goods | id | 所属商品 |

**业务规则**：
- 同一商品下，颜色+尺码组合不可重复
- 删除前检查库存（stock.quantity > 0），若有库存则禁止删除
- 删除前检查是否有进行中的采购/销售记录
- 价格变动不追溯历史单据
- `sku_code` 建议规则：`{goods_code}-{color}-{size}` 如 `SP001-RED-M`

**使用示例**：
```sql
-- 查询某商品下的所有 SKU
SELECT * FROM goods_sku WHERE goods_id = 1 AND deleted_at IS NULL;

-- 查询所有红色 M 码的 SKU（跨商品）
SELECT gs.*, g.name AS goods_name
FROM goods_sku gs
JOIN goods g ON gs.goods_id = g.id
WHERE gs.color = '红色' AND gs.size = 'M' AND gs.deleted_at IS NULL;
```

**为什么这样设计**：
- **color/size 存为字符串而非关联表**：v1 阶段个体户场景中颜色和尺码值有限且变化少，字符串存储简单直接；后续可升级为 `color` 和 `size` 字典表，通过 ID 关联，便于统一管理和多语言
- **barcode 可为空**：个体户进货很多无条码，强制要求不现实
- **cost_price / sale_price 放在 SKU 层**：不同颜色/尺码可能定价不同（如 XL 加价），放在 SKU 比放在 SPU 更精确
- **sku_code 唯一**：保证每个 SKU 有唯一业务标识，方便扫码和导入导出

## 三、库存中心

库存中心管理实时库存和变动流水，是进销存的核心数据。

### 1. 库存（stock）

**表用途**：记录每个仓库中每个 SKU 的当前库存量，是实时快照表。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| warehouse_id | BIGINT UNSIGNED | NOT NULL | - | 仓库ID |
| sku_id | BIGINT UNSIGNED | NOT NULL | - | SKU ID |
| quantity | INT | NOT NULL | 0 | 当前库存数量 |
| lock_quantity | INT | NOT NULL | 0 | 锁定数量（待出库占用） |
| warning_quantity | INT | NOT NULL | 0 | 预警数量，低于此值触发库存预警 |
| updated_at | DATETIME(3) | NOT NULL | - | 最后更新时间 |

> **注意**：stock 表不继承 GVA_MODEL，不需要软删除（库存记录应随仓库和 SKU 存在），也没有 created_at（初始入库时间由 stock_log 追溯）。

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_warehouse_sku | **唯一索引** | (warehouse_id, sku_id) | 同一仓库同一SKU只有一条库存记录 |
| idx_sku_id | 普通索引 | sku_id | 按 SKU 查库存 |
| idx_warning | 普通索引 | (warehouse_id, warning_quantity) | 库存预警查询 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| warehouse_id | warehouse | id | 所属仓库 |
| sku_id | goods_sku | id | 对应 SKU |

**业务规则**：
- `warehouse_id + sku_id` 联合唯一，每个仓库每个 SKU 只有一条库存记录
- `available_quantity`（可用库存）= `quantity - lock_quantity`
- 出库时先检查可用库存是否充足
- 出库时先增加 lock_quantity，确认后扣减 quantity 和 lock_quantity
- 入库时直接增加 quantity
- 库存变更必须同步写入 stock_log
- 不允许直接修改 quantity，必须通过入库/出库/盘点操作触发

**使用示例**：
```sql
-- 查询某仓库中库存不足的 SKU（可用库存 < 预警数）
SELECT s.*, gs.sku_code, gs.color, gs.size, g.name AS goods_name
FROM stock s
JOIN goods_sku gs ON s.sku_id = gs.id
JOIN goods g ON gs.goods_id = g.id
WHERE s.warehouse_id = 1
  AND (s.quantity - s.lock_quantity) < s.warning_quantity;

-- 入库操作（在事务中执行）
UPDATE stock SET quantity = quantity + 10, updated_at = NOW()
WHERE warehouse_id = 1 AND sku_id = 5;

-- 出库操作（先锁库存）
UPDATE stock SET lock_quantity = lock_quantity + 5
WHERE warehouse_id = 1 AND sku_id = 5 AND (quantity - lock_quantity) >= 5;
-- 确认出库
UPDATE stock SET quantity = quantity - 5, lock_quantity = lock_quantity - 5, updated_at = NOW()
WHERE warehouse_id = 1 AND sku_id = 5;
```

**为什么这样设计**：
- **联合唯一索引 (warehouse_id, sku_id)**：避免同一仓库同一 SKU 出现多条库存记录，保证数据一致性
- **lock_quantity**：预留锁定机制，防止超卖 — 创建出库单时锁定，完成时扣减；取消时释放
- **warning_quantity**：库存预警阈值，方便个体户及时补货，避免断货
- **不继承 GVA_MODEL**：stock 是仓库-SKU 的快照，生命周期跟随仓库和 SKU，不需要独立的软删除和创建时间

### 2. 库存流水（stock_log）

**表用途**：记录每一次库存变化的完整历史，用于审计追溯和对账。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| warehouse_id | BIGINT UNSIGNED | NOT NULL | - | 仓库ID |
| sku_id | BIGINT UNSIGNED | NOT NULL | - | SKU ID |
| business_type | VARCHAR(30) | NOT NULL | - | 业务类型：purchase_in=采购入库，sale_out=销售出库，sale_return=销售退货，check_in=盘点盘盈，check_out=盘点盘亏，direct_in=直接入库，direct_out=直接出库 |
| business_no | VARCHAR(50) | NOT NULL | - | 业务单号（采购单号/销售单号/盘点单号） |
| before_qty | INT | NOT NULL | 0 | 变更前数量 |
| change_qty | INT | NOT NULL | 0 | 变更数量（正数=入库/盘盈，负数=出库/盘亏） |
| after_qty | INT | NOT NULL | 0 | 变更后数量 |
| operator | VARCHAR(50) | NULL | NULL | 操作人（用户名） |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间（即库存变更时间） |

> **注意**：stock_log 不继承 GVA_MODEL，流水一旦生成不可修改或删除（只追加），无需软删除。

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| idx_sku_warehouse | 普通索引 | (sku_id, warehouse_id) | 按 SKU+仓库查流水 |
| idx_business_no | 普通索引 | business_no | 按业务单号查流水 |
| idx_business_type | 普通索引 | business_type | 按业务类型筛选 |
| idx_created_at | 普通索引 | created_at | 按时间范围查询 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| warehouse_id | warehouse | id | 所属仓库 |
| sku_id | goods_sku | id | 对应 SKU |

**业务规则**：
- 流水记录只增不删不改（不可变日志）
- `after_qty = before_qty + change_qty`（数据完整性校验）
- 每笔入库/出库/盘点操作必须同步生成流水
- 同一业务单号可能对应多条流水（如一张采购单包含多个 SKU）

**使用示例**：
```sql
-- 查询某 SKU 在某仓库的流水记录
SELECT * FROM stock_log
WHERE sku_id = 5 AND warehouse_id = 1
ORDER BY created_at DESC;

-- 查询某采购单产生的所有流水
SELECT * FROM stock_log WHERE business_no = 'PO-20260101-001';

-- 统计某时间段内的入库总量
SELECT sku_id, SUM(change_qty) AS total_in
FROM stock_log
WHERE business_type = 'purchase_in' AND created_at BETWEEN '2026-01-01' AND '2026-01-31'
GROUP BY sku_id;
```

**为什么这样设计**：
- **不可变日志**：库存数据容易出错，保留完整流水可以回溯任意时间点的库存状态，方便对账和纠错
- **business_type 枚举**：用字符串枚举而非数字编码，SQL 查询时可读性更好
- **before_qty/change_qty/after_qty 三元组**：一条记录就能还原变更全貌，无需关联上下文
- **独立 operator 字段**：记录操作人而非依赖 GVA_MODEL，因为流水不可修改，操作人信息必须内聚

## 四、采购中心

采购中心管理从供应商进货的完整流程。

### 1. 采购单（purchase_order）

**表用途**：记录每次采购的汇总信息，一个采购单包含多个采购明细。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| order_no | VARCHAR(50) | NOT NULL | - | 采购单号，全局唯一，建议格式：PO-YYYYMMDD-XXX |
| supplier_id | BIGINT UNSIGNED | NOT NULL | - | 供应商ID |
| warehouse_id | BIGINT UNSIGNED | NOT NULL | - | 入库仓库ID |
| status | TINYINT | NOT NULL | 1 | 状态：1=待审核，2=已审核（待入库），3=已入库，4=已取消 |
| total_amount | DECIMAL(12,2) | NOT NULL | 0.00 | 采购总金额（明细金额之和） |
| remark | VARCHAR(500) | NULL | NULL | 备注 |
| creator | VARCHAR(50) | NOT NULL | - | 创建人（用户名） |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间 |
| updated_at | DATETIME(3) | NOT NULL | - | 更新时间 |
| deleted_at | DATETIME(3) | NULL | NULL | 删除时间（软删除） |

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_order_no | 唯一索引 | order_no | 采购单号唯一 |
| idx_supplier_id | 普通索引 | supplier_id | 按供应商查询 |
| idx_status | 普通索引 | status | 按状态筛选 |
| idx_created_at | 普通索引 | created_at | 按时间范围查询 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| supplier_id | supplier | id | 供货供应商 |
| warehouse_id | warehouse | id | 入库仓库 |

**业务规则**：
- 采购单创建时状态为「待审核」
- 审核通过后变为「已审核」，此时可执行入库
- 入库操作：校验状态为「已审核」→ 更新 stock 表（增加 quantity）→ 生成 stock_log → 修改采购单状态为「已入库」
- 取消采购：状态从「待审核」或「已审核」变为「已取消」
- 只有「待审核」状态的采购单可以删除
- `total_amount` 由明细自动计算，不可手动修改

**状态流转**：
```
待审核(1) ──审核通过──► 已审核(2) ──入库──► 已入库(3)
    │                      │
    └──────取消────────────┘
              │
              ▼
          已取消(4)
```

**使用示例**：
```sql
-- 创建采购单
INSERT INTO purchase_order (order_no, supplier_id, warehouse_id, status, total_amount, creator)
VALUES ('PO-20260601-001', 1, 1, 1, 0.00, 'admin');

-- 审核通过
UPDATE purchase_order SET status = 2 WHERE id = 1 AND status = 1;

-- 查询待入库的采购单
SELECT * FROM purchase_order WHERE status = 2 AND deleted_at IS NULL;
```

**为什么这样设计**：
- **状态机模型**：采购是流程性操作，「待审核→已审核→已入库」的状态流转符合个体户的实际业务（采购员下单，老板审核，仓管入库）
- **关联 warehouse_id**：采购时即指定入库仓库，简化入库操作（无需再选仓库）
- **creator 字段**：记录创建人，与 GVA 用户体系关联，用于权限控制
- **不继承 GVA_MODEL 的 ID 外键**：creator 用字符串而非用户表外键，解耦 RBAC 体系，删除用户不影响采购记录

> **注意**：采购明细不继承 GVA_MODEL，生命周期完全跟随采购单。

```sql
SELECT pi.*, gs.sku_code, gs.color, gs.size, g.name AS goods_name
```

**为什么这样设计**：

- **不继承 GVA_MODEL**：明细是聚合根（采购单）的子实体，没有独立生命周期

## 五、销售中心

销售中心管理向客户销售的完整流程，支持正常销售、退货退款和换货。

### 1. 销售单（sale_order）

**表用途**：记录每次销售的汇总信息，一个销售单包含多个销售明细。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| order_no | VARCHAR(50) | NOT NULL | - | 销售单号，全局唯一，建议格式：SO-YYYYMMDD-XXX |
| customer_id | BIGINT UNSIGNED | NULL | NULL | 客户ID（零售可空） |
| warehouse_id | BIGINT UNSIGNED | NOT NULL | - | 出库仓库ID |
| order_type | TINYINT | NOT NULL | 1 | 单据类型：1=正常销售，2=退货退款，3=换货出库，4=换货入库 |
| original_order_id | BIGINT UNSIGNED | NULL | NULL | 关联原单ID（退货/换货时关联原销售单） |
| status | TINYINT | NOT NULL | 1 | 状态：1=待出库，2=已出库，3=已取消 |
| total_amount | DECIMAL(12,2) | NOT NULL | 0.00 | 销售总金额（明细金额之和） |
| remark | VARCHAR(500) | NULL | NULL | 备注 |
| creator | VARCHAR(50) | NOT NULL | - | 创建人（用户名） |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间 |
| updated_at | DATETIME(3) | NOT NULL | - | 更新时间 |
| deleted_at | DATETIME(3) | NULL | NULL | 删除时间（软删除） |

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_order_no | 唯一索引 | order_no | 销售单号唯一 |
| idx_customer_id | 普通索引 | customer_id | 按客户查询 |
| idx_status | 普通索引 | status | 按状态筛选 |
| idx_original_order_id | 普通索引 | original_order_id | 查询关联单据 |
| idx_created_at | 普通索引 | created_at | 按时间范围查询 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| customer_id | customer | id | 购买客户（零售可空） |
| warehouse_id | warehouse | id | 出库仓库 |
| original_order_id | sale_order | id | 关联原单（自引用） |

**业务规则**：

**正常销售流程**：
1. 创建销售单（状态：待出库），同时锁定库存（stock.lock_quantity 增加）
2. 确认出库：校验库存充足 → 减少库存（quantity 和 lock_quantity）→ 生成 stock_log（business_type=sale_out）→ 修改状态为「已出库」
3. 取消销售：释放锁定库存 → 状态变为「已取消」

**退货退款流程**：
1. 创建退货单（order_type=2, original_order_id=原单ID），明细数量为正数
2. 确认退货：增加库存 → 生成 stock_log（business_type=sale_return）→ 状态变为「已出库」

**换货流程**：
1. 创建换货出库单（order_type=3, original_order_id=原单ID），明细为换出商品（负向出库）
2. 创建换货入库单（order_type=4, original_order_id=原单ID），明细为换入商品（正向入库）
3. 确认后分别增减库存，生成对应流水

- 只有「待出库」状态的销售单可以删除
- customer_id 可为 NULL（支持匿名零售）
- `total_amount` 由明细自动计算

**状态流转**：
```
待出库(1) ──确认出库──► 已出库(2)
    │
    └────取消──► 已取消(3)
```

**使用示例**：
```sql
-- 创建正常销售单
INSERT INTO sale_order (order_no, customer_id, warehouse_id, order_type, status, total_amount, creator)
VALUES ('SO-20260601-001', 1, 1, 1, 1, 0.00, 'admin');

-- 创建退货单（关联原单 SO-20260601-001）
INSERT INTO sale_order (order_no, customer_id, warehouse_id, order_type, original_order_id, status, total_amount, creator)
VALUES ('SO-20260601-002', 1, 1, 2, 1, 1, 0.00, 'admin');

-- 查询某客户的所有销售记录
SELECT * FROM sale_order WHERE customer_id = 1 AND deleted_at IS NULL ORDER BY created_at DESC;
```

**为什么这样设计**：
- **order_type + original_order_id 支持退货/换货**：用自引用关联原单，比创建单独的退货表/换货表更简洁统一，查询时可通过 original_order_id 追溯完整链路
- **customer_id 可为空**：个体户零售场景大量无客户信息，强制关联会增加录入负担
- **原字段名 `custmer_id` 修正为 `customer_id`**
- **换货拆为两单**：换货 = 换出（类型3）+ 换入（类型4），各自独立管理库存变动，逻辑清晰；通过 original_order_id 关联到同一原单

---

### 2. 销售明细（sale_item）

```sql
FROM sale_item si
JOIN goods_sku gs ON si.sku_id = gs.id
JOIN goods g ON gs.goods_id = g.id
WHERE si.sale_id = 1;
```

**为什么这样设计**：
- **price 冗余存储**：实际售价可能与 SKU 标价不同（折扣、议价），必须按实际售价记录
- **与采购明细对称**：保持采购和销售的数据结构一致，降低理解成本和代码复用难度

## 六、库存盘点

库存盘点用于定期核对系统库存与实际库存，发现差异并调整。

### 1. 盘点单（stock_check）

**表用途**：记录每次盘点任务的基本信息。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| check_no | VARCHAR(50) | NOT NULL | - | 盘点单号，全局唯一，建议格式：CK-YYYYMMDD-XXX |
| warehouse_id | BIGINT UNSIGNED | NOT NULL | - | 盘点仓库ID |
| status | TINYINT | NOT NULL | 1 | 状态：1=盘点中，2=已完成（差异已调整） |
| checker | VARCHAR(50) | NULL | NULL | 盘点人（用户名） |
| remark | VARCHAR(500) | NULL | NULL | 备注 |
| created_at | DATETIME(3) | NOT NULL | - | 创建时间 |
| updated_at | DATETIME(3) | NOT NULL | - | 更新时间 |
| deleted_at | DATETIME(3) | NULL | NULL | 删除时间（软删除） |

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| uk_check_no | 唯一索引 | check_no | 盘点单号唯一 |
| idx_warehouse_id | 普通索引 | warehouse_id | 按仓库查询 |
| idx_status | 普通索引 | status | 按状态筛选 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| warehouse_id | warehouse | id | 盘点仓库 |

**业务规则**：
- 创建盘点单时状态为「盘点中」，同时可录入盘点明细
- 完成盘点：对比 system_qty 和 actual_qty → 有差异的生成库存调整 → 生成 stock_log（盘盈 stock_check_in / 盘亏 stock_check_out）→ 更新 stock 表 → 状态变为「已完成」
- 盘点中的盘点单可以修改明细，完成后的不可修改
- 盘点单不直接生成"调整单"，差异在盘点单内部处理

**状态流转**：
```
盘点中(1) ──完成盘点──► 已完成(2)
```

**使用示例**：
```sql
-- 创建盘点单
INSERT INTO stock_check (check_no, warehouse_id, status, checker)
VALUES ('CK-20260601-001', 1, 1, 'admin');

-- 完成盘点
UPDATE stock_check SET status = 2, updated_at = NOW() WHERE id = 1 AND status = 1;
```

**为什么这样设计**：
- **增加 checker 字段**：记录盘点人，审计追溯必需
- **增加 GVA_MODEL 时间戳**：原设计缺少，不利于管理
- **在盘点单内处理差异**：v1 不单独创建"库存调整单"，简化流程；差异通过 stock_log 的 business_type 区分盘盈/盘亏

---

### 2. 盘点明细（stock_check_item）

**表用途**：记录盘点单中每个 SKU 的系统库存、实际盘点数和差异数。

**字段定义**：

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|------|------|----------|--------|------|
| id | BIGINT UNSIGNED | NOT NULL | AUTO_INCREMENT | 主键 |
| check_id | BIGINT UNSIGNED | NOT NULL | - | 盘点单ID |
| sku_id | BIGINT UNSIGNED | NOT NULL | - | SKU ID |
| system_qty | INT | NOT NULL | 0 | 系统库存数量（盘点时的 stock.quantity） |
| actual_qty | INT | NOT NULL | 0 | 实际盘点数量（人工录入） |
| diff_qty | INT | NOT NULL | 0 | 差异数量（actual_qty - system_qty，正=盘盈，负=盘亏） |

> **注意**：盘点明细不继承 GVA_MODEL，生命周期完全跟随盘点单。

**主键与索引**：

| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| PRIMARY | 主键 | id | - |
| idx_check_id | 普通索引 | check_id | 按盘点单查明细 |

**外键关系**：

| 外键字段 | 关联表 | 关联字段 | 关系说明 |
|----------|--------|----------|----------|
| check_id | stock_check | id | 所属盘点单 |
| sku_id | goods_sku | id | 盘点的 SKU |

**业务规则**：
- `system_qty` 在盘点明细创建时自动从 stock 表抓取，不可手动修改
- `diff_qty = actual_qty - system_qty`，由系统自动计算
- 完成盘点时，diff_qty ≠ 0 的明细触发库存调整：更新 stock.quantity → 生成 stock_log

**使用示例**：
```sql
-- 创建盘点明细
INSERT INTO stock_check_item (check_id, sku_id, system_qty, actual_qty, diff_qty)
VALUES (1, 5, 100, 98, -2);

-- 查询盘点差异明细
SELECT sci.*, gs.sku_code, gs.color, gs.size, g.name AS goods_name
FROM stock_check_item sci
JOIN goods_sku gs ON sci.sku_id = gs.id
JOIN goods g ON gs.goods_id = g.id
WHERE sci.check_id = 1 AND sci.diff_qty != 0;
```

**为什么这样设计**：
- **system_qty 快照**：盘点时记录系统库存快照，避免盘点过程中库存变动导致数据不一致
- **diff_qty 自动计算**：减少人工计算出错的可能
- **正负表示盘盈盘亏**：统一用一个字段表达双向差异，比分开两个字段更简洁

## 九、事务一致性要求

以下操作必须在数据库事务中执行：

| 操作 | 涉及的 SQL | 回滚条件 |
|------|------------|----------|
| 采购入库 | 更新 purchase_order 状态 + 更新 stock 多条 + 插入 stock_log 多条 | 库存更新失败 |
| 销售出库 | 更新 sale_order 状态 + 更新 stock 多条 + 插入 stock_log 多条 | 库存不足 |
| 销售退货 | 更新 sale_order 状态 + 更新 stock 多条 + 插入 stock_log 多条 | 任一 SKU 不存在 |
| 盘点完成 | 更新 stock_check 状态 + 更新 stock 多条 + 插入 stock_log 多条 | 差异调整失败 |
| 直接入库/出库 | 更新 stock + 插入 stock_log | 库存更新失败 |

所有涉及库存变更的操作必须：**先写 stock_log，再更新 stock**，保证流水可追溯。

## 十、与 GVA 框架的集成说明

1. **GVA_MODEL 继承**：除 stock、stock_log、purchase_item、sale_item、stock_check_item 外，其余表继承 `global.GVA_MODEL`，自动获得 ID、CreatedAt、UpdatedAt、DeletedAt
2. **软删除**：继承 GVA_MODEL 的表均支持 GORM 软删除，删除操作设置 deleted_at 而非物理删除
3. **用户关联**：creator/operator/checker 字段存储用户名（字符串），通过 GVA 的 `utils.GetUserName(ctx)` 获取，不使用外键关联 sys_users
4. **分页查询**：配合 GVA 的 `info.Page` + `info.PageSize` 分页参数使用
5. **自动编码**：可对接 GVA 的自动编码插件生成 order_no、code 等编码

```go
        WarehouseID: 1,
        Status:      PurchaseStatusPending,

    if err := tx.Create(po).Error; err != nil {

    }

        }
    }

// 库存查询（含 SKU 和商品信息）
```

> **soft delete tables**（继承 GVA_MODEL 的表）的 Delete 操作会设置 `deleted_at` 而非物理删除；查询时 GORM 自动附加 `WHERE deleted_at IS NULL`。**hard tables**（不继承 GVA_MODEL 的表）的 Delete 操作直接物理删除（或由上层逻辑禁止删除，如 stock_log）。
