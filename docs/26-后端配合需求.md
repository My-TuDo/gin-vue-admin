## 二、需求 1：单据列表服务端筛选与分页（P1）

### 现状与问题

`GET /jxc/{sale,purchase,return,reversal,purchase-return}/page` 目前只接收
`page`、`pageSize`；前端在 `web/src/view/jxc/documents/index.vue` 里一次取 100 条，
再在浏览器内做关键词/状态筛选和分页。

后果：

- 超过 100 条后，筛选项与计数只对已取回数据成立，用户会看到“找不到”实际存在的单；
- 打开单据页要串行加载 5 类单据 + 主数据，数据量大时首屏变慢；
- 分页页码是前端的，不是数据库的 `total`。

### 接口契约建议

五个端点统一增加查询参数（全部可选）：

| 参数 | 类型 | 说明 |
|---|---|---|
| `page` | int | 默认 1 |
| `pageSize` | int | 默认 20，最大 100 |
| `status` | int | 单据状态；不传=全部 |
| `keyword` | string | 单号、往来单位名称/编码、备注/原因 |
| `warehouseId` | uint | 仓库 |
| `partnerId` | uint | 客户/供应商（销售/采购/退货） |
| `startAt` | string | `YYYY-MM-DD`，按业务时间/创建时间，需明确 |
| `endAt` | string | `YYYY-MM-DD`，含当天 |

响应保持 `response.PageResult`：

```json
{
  "code": 0,
  "data": {
    "list": [],
    "total": 1234,
    "page": 1,
    "pageSize": 20
  },
  "msg": "成功"
}
```

### 筛选语义（需要确认）

- 销售/采购：单号、往来单位名称/编码、备注；
- 销售退货：退货单号、原销售单号、原因；
- 采购退货：退货单号、原采购单号、原因；
- 红冲：红冲单号、原单号、原因、来源类型；
- 已红冲单据的状态按**原单据状态**筛选还是按“已红冲”筛选？建议增加
  `reversed=true/false` 独立参数，不混进 `status`；
- 日期范围按 `posted_at` 还是 `created_at`？建议默认按创建时间，另给
  `dateField=posted|created` 预留；
- 时区固定 `Asia/Shanghai`，前后端一致。

### 索引建议

- `(status, created_at)`；
- 单号列已有唯一索引，可直接等值/前缀查询；
- `(warehouse_id, created_at)`、`(supplier_id, created_at)`、`(customer_id, created_at)`；
- 若关键词要搜往来单位名称，需要在 join 后过滤；建议先给单号/备注前缀检索，
  名称检索通过 `partnerId` 精确筛选，避免全表 `%keyword%`。

### 验收

- 造 5 万条销售单，筛选“已出库 + 关键词 + 日期 + 仓库”返回正确 `total` 与首页；
- 单页 P95 < 300ms（本机 MySQL）；
- 前端去掉 100 条上限，直接使用服务端 `total` 分页；
- 所有页签的空态/计数与数据库一致。

### 前端改动

- `documents/index.vue` 改为按当前 tab 请求对应端点，参数透传；
- 删除 `pageRows` 的浏览器切片与前端计数（或保留为权限受限时的降级）。

## 三、需求 2：工作台聚合接口（P1）

### 现状与问题

`web/src/view/jxc/workspace/index.vue` 当前并发拉取：

- `ledger/balance`（全量余额）
- `sale/page?pageSize=100`
- `purchase/page?pageSize=100`
- `return/page?pageSize=100`
- `purchase-return/page?pageSize=100`

再在前端算今日销售额、毛利、待办、低库存。超过 100 条后，KPI 与待办会少算；
同时把 5 个列表接口的响应都压到首屏。

### 建议接口

`GET /jxc/dashboard/summary?date=YYYY-MM-DD`（默认今天，`Asia/Shanghai`）

```json
{
  "code": 0,
  "data": {
    "date": "2026-10-27",
    "stockValue": 10477.00,
    "skuCount": 18,
    "todaySalesAmount": 2711.00,
    "todaySalesOrders": 16,
    "todayReturnAmount": 1400.00,
    "todayReturnOrders": 14,
    "todayGross": 1375.00,
    "todayPurchaseAmount": 0,
    "pending": {
      "approve": 0,
      "receive": 0,
      "ship": 0,
      "purchaseReturnDraft": 0,
      "total": 0
    },
    "lowStock": {
      "threshold": 10,
      "count": 6,
      "items": [
        {
          "warehouseId": 1,
          "warehouseName": "主仓",
          "skuId": 1,
          "goodsName": "连帽卫衣",
          "color": "黑",
          "size": "M",
          "available": 4
        }
      ]
    }
  }
}
```

### 口径（必须与 `docs/23` 一致）

- 今日销售额 = 今日已出库且未红冲销售 − 今日已入库销售退货；
- 今日毛利 = 今日销售额 −（今日销售成本 − 今日退回成本）；
- 红冲按红冲发生时间计入，不追溯修改原单月份；
- 采购退货不影响销售/毛利（它是采购侧出库），但**待办要统计草稿数**；
- 待办计数不受分页影响；
- 低库存按 `available <= threshold` 且 `qty >= 0`，按 `available` 升序取前 5；
- 先按全部仓库聚合，后续可加 `warehouseId`。

### 验收

- 与手工 SQL 对账一致；
- 退货/采购退货/红冲/盘点后重新请求，数字立即变化；
- 单次响应 P95 < 100ms（本机）；
- 前端删除 5 个列表请求，只保留 `ledger/moves`（最近流水）或将其并入接口。

### 前端改动

- 工作台改为单次 `dashboard/summary`；
- 待办链接保持现状；
- 低库存直接用返回列表。

### 2.1 月报采购额纳入采购退货（补充）

现状 `GET /jxc/period/summary` 的 `purchaseAmount` 只汇总 `purchase_order`，
没有扣减当月已过账的 `purchase_return`。这和 `docs/25` 的“真实退货业务”语义不一致：
供应商退了钱、库存与账本金额都减少了，月报的采购金额却仍是全额。

建议：

- `purchaseAmount` 改为**净采购额** = 已入库采购 − 已过账采购退货；
- 新增 `purchaseReturnAmount` 字段，报表页可单列“采购退货”；
- 红冲按红冲发生月计入；已结账月份不回写；
- 期末库存不需要改：它按 `stock_move` 月结快照/账本累加，已经包含采购退货；
- `dashboard/summary` 的 `todayPurchaseAmount` 同步用净额。

验收：

- 造“采购 100 → 退 20”，月报采购金额应为 80，采购退货 20；
- 退货跨月时，退货计入退货发生月，原采购月不追溯；
- 前端报表“采购金额”与账本采购侧净额一致。

## 四、需求 3：对账作用域与最近结果（P1/P2）

### 现状与问题

- `GET /jxc/ledger/reconcile` 当前按仓库/全仓做一次完整校验；
- 壳层 `shell.vue` 每次进入 `/jxc` 调一次，单据/余额大时是明显首屏成本；
- 只有“当次”结果，没有“上次检查时间/耗时”，顶栏状态无法解释新鲜度。

### 建议

1. 保留现有同步接口作为“手动检查”，支持 `warehouseId`（已有）；
2. 增加最近结果查询：
   `GET /jxc/ledger/reconcile/last?warehouseId=`
   返回：
   ```json
   {
     "ok": true,
     "checkedAt": "2026-10-27T19:21:00+08:00",
     "durationMs": 42,
     "scope": "warehouse:1",
     "checkedSkus": 18,
     "count": 0,
     "violations": []
   }
   ```
3. 手动检查完成后缓存结果（进程内，TTL 60s 可配）；壳层只读 `/last`，
   不再自动触发全仓扫描；
4. 如需要异步：`POST /jxc/ledger/reconcile` 返回 job id，前端轮询；
   当前同步 + 缓存足够，不建议先上任务系统。

### 验收

- 进入 `/jxc` 不产生全仓 reconcile 查询；
- 手动按仓库检查后，顶栏显示“上次检查时间/范围”，不再是无限期的“账实相符”；
- 缓存在 TTL 内命中，手动检查可强制刷新。

## 五、需求 4：采购退货列表展示字段（P2，可选）

当前 `PurchaseReturn` 列表只返回 `supplierId / warehouseId / purchaseNo / items`，
前端用主数据 map 出供应商/仓库/商品名。若实现需求 1 的服务端关键词（按供应商名）筛选，
列表需要 join 返回：

- `supplierName`；
- `warehouseName`；
- `itemCount`（可选，列表展示“2 项”）；
- `items` 在列表里可只返回数量，不返回完整明细，减少响应体积。

如果不做服务端筛选，本项可以不排期。

4. 用 9003/8881 验证：接口返回 `code=7`（权限不足），前端不弹整页错误，点击操作时给可读提示。

## 七、契约与错误约定

- 保持统一响应 `{code,data,msg}`；业务失败仍用 `code=7`/HTTP 200，
  前端直接展示 `msg`；不要改成 4xx 而让 axios 走拦截器，除非同步改前端。
- 权限不足也保持现有 `NoAuth` 行为（当前返回 HTTP 401/code 7，Casbin 为 HTTP 200/code 7）；
  前端对采购退货已单独兼容 code 7，避免单据页整页报错。
- 日期时间统一 `Asia/Shanghai`；接口返回 RFC3339 或 `YYYY-MM-DD HH:mm:ss` 均可，
  前端 `new Date` 可解析；不要返回无时区的裸时间。
- 金额仍用 `decimal(14,2)` 转 number；前端 `MoneyText` 统一两位小数。

---

## 八、非目标

- 采购退货红冲（退错后的反向业务）不在本轮；
- 批次/FIFO 退货不在本轮；
- 打印/导出、批量导入、多仓调拨不在本轮；
- 前端不要求后端返回 HTML/格式化字符串。

## 九、验收脚本建议

1. 用脚本造 5 万条销售单/采购单（可复用 `scripts/seed-demo.py` 的批量模式）；
2. 对每个列表端点跑：

   - 状态 + 关键词 + 日期 + 仓库组合：返回列表与 SQL 一致；
   - 第 1/最后一页数据不重叠、不缺失；
3. 工作台：`dashboard/summary` 的每个字段与 `docs/23` 口径 SQL 对照；
4. 对账：进入 `/jxc` 不触发全仓扫描；手动检查后 `/last` 时间/范围正确；
5. 权限：9002 通过、9003/8881 返回 code 7。
