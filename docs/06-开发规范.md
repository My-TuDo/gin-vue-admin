# 06-开发规范

> 本文档约定 GVA-JXC（服装类进销存系统）在 GVA（Gin-Vue-Admin）框架上的开发规范。
> 技术栈：后端 Go + Gin + GORM + Zap，前端 Vue3 + ElementPlus + Vite + Pinia + UnoCSS。
> 适用于所有参与本仓库 `server/` 与 `web/` 开发的成员，代码评审以此为唯一依据（框架自带代码除外）。

---

## 一、Go 后端规范

### 1.1 命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 包名 | 全小写、单数单词，不使用下划线；业务子包统一为 `jxc` 及其子模块 | `package jxc` |
| 文件名 | `snake_case`，一个文件聚焦一个业务主题，按模块分文件 | `goods.go`、`purchase.go` |
| 变量/常量 | 局部变量 `camelCase`；未导出包级变量 `camelCase`；常量全大写驼峰 | `skuList`、`maxPageSize`、`DefaultStatus` |
| 函数 | 动词开头，`PascalCase`（导出）/`camelCase`（未导出） | `CreateGoods`、`getStockBySkuID` |
| 结构体 | `PascalCase`，业务结构体不带 `Jxc`/`Model` 冗余后缀 | `Goods`、`PurchaseOrder`、`PurchaseOrderItem` |
| 结构体字段 | 导出字段 `PascalCase`，必须带 `json` tag（`camelCase`）与 `gorm` tag | `SKUCode string` |
| 接口 | `PascalCase`，动词 + 对象 | `GoodsRepository` |
| 错误变量 | `err` 使用标准库语义；自定义错误用 `errors.New` 或 `fmt.Errorf` 包装 | `errors.New("库存不足")` |

结构体示例：

```go
// 商品（SPU）
type Goods struct {
	global.GVA_MODEL
	Code        string   `json:"code" gorm:"size:50;uniqueIndex;comment:商品编码"`  // 商品编码
	Name        string   `json:"name" gorm:"size:100;comment:商品名称"`              // 商品名称
	CategoryID  uint     `json:"categoryId" gorm:"comment:分类ID"`                  // 分类ID
	BrandID     uint     `json:"brandId" gorm:"comment:品牌ID"`                     // 品牌ID
	Status      int      `json:"status" gorm:"default:1;comment:状态 1上架 0下架"`    // 状态 1上架 0下架
	Category    Category `json:"category" gorm:"foreignKey:CategoryID;comment:分类"` // 分类
	Brand       Brand    `json:"brand" gorm:"foreignKey:BrandID;comment:品牌"`       // 品牌
	SKUs        []GoodsSKU `json:"skus" gorm:"foreignKey:GoodsID;comment:SKU列表"`   // SKU列表
}

func (Goods) TableName() string {
	return "goods"
}
```

### 1.2 目录规范（GVA 分层）

遵循 GVA 官方分层，调用链固定为：

```
router → api/v1 → service → model（GORM 数据访问）
```

新增业务模块一律放入 `jxc` 子包，不散落到其他包：

```
server/
├── api/v1/jxc/               # 接口层（HTTP 参数解析 + 响应）
│   ├── enter.go              #   ApiGroup 聚合 + service 引用
│   ├── category.go           #   分类接口
│   ├── goods.go              #   商品接口
│   ├── purchase.go           #   采购接口
│   └── ...
├── service/jxc/              # 业务逻辑层（事务、校验、库存计算）
│   ├── enter.go              #   ServiceGroup 聚合
│   ├── goods.go
│   ├── purchase.go
│   └── ...
├── model/jxc/                # 数据模型层
│   ├── goods.go              #   Goods / GoodsSKU / Category / Brand
│   ├── purchase.go           #   PurchaseOrder / PurchaseOrderItem
│   └── ...
└── router/jxc/               # 路由层（路径注册 + 中间件）
    ├── enter.go
    ├── goods.go
    └── ...
```

每层必须提供 `enter.go` 聚合入口，供上层引用，禁止跨层直接 `import` 具体业务文件：

```go
// server/api/v1/jxc/enter.go
package jxc

import "github.com/flipped-aurora/gin-vue-admin/server/service"

type ApiGroup struct {
	GoodsApi
	PurchaseApi
}

var (
	goodsService    = service.ServiceGroupApp.JxcServiceGroup.GoodsService
	purchaseService = service.ServiceGroupApp.JxcServiceGroup.PurchaseService
)
```

```go
// server/service/jxc/enter.go
package jxc

type ServiceGroup struct {
	GoodsService
	PurchaseService
}
```

```go
// server/router/jxc/enter.go
package jxc

type RouterGroup struct {
	GoodsRouter
	PurchaseRouter
}
```

层间职责边界：

| 层 | 职责 | 禁止 |
|----|------|------|
| `router` | 注册路由、挂载中间件（jwt、casbin、操作记录） | 写业务逻辑、直接操作 DB |
| `api/v1` | 绑定/校验参数、调用 service、组织 response | 写 SQL、写事务 |
| `service` | 业务规则、事务边界、校验逻辑 | 直接输出 HTTP 响应 |
| `model` | 定义结构体、表名、索引、枚举常量 | 写 HTTP 相关代码 |

### 1.3 错误处理规范

统一使用 GVA 的 `server/model/common/response` 响应结构，**禁止**在 api 层直接 `c.JSON` 拼装自定义结构。

```go
// server/model/common/response/response.go（框架已定义，禁止改动）
type Response struct {
	Code int         `json:"code"`
	Data interface{} `json:"data"`
	Msg  string      `json:"msg"`
}

const (
	ERROR   = 7
	SUCCESS = 0
)
```

**错误码定义**：

| 错误码 | 含义 | 使用场景 |
|--------|------|----------|
| `0` | 成功 | 所有成功响应（`Ok` 系列） |
| `7` | 通用业务失败 | 参数校验失败、业务规则不满足（`Fail` 系列） |
| HTTP 401 | 未认证 / token 失效 | `response.NoAuth`，由中间件触发 |

业务失败不额外发明错误码，统一 `code = 7`，靠 `msg` 给出人类可读的具体原因；如需前端据此分支处理，在 `msg` 中给出稳定文案并在接口文档登记，**不修改全局 `ERROR` 常量**。

api 层处理模板：

```go
// CreateGoods 创建商品
// @Tags     JxcGoods
// @Summary  创建商品（含SKU）
// @Security ApiKeyAuth
// @accept   application/json
// @Produce  application/json
// @Param    data body model/jxc.GoodsRequest true "商品信息"
// @Success  200 {object} response.Response{msg=string} "创建商品"
// @Router   /jxc/goods [post]
func (g *GoodsApi) CreateGoods(c *gin.Context) {
	var req request.GoodsCreate
	if err := c.ShouldBindJSON(&req); err != nil {
		response.FailWithMessage(err.Error(), c)
		return
	}
	// 参数校验（GVA utils.Verify + 自定义 rule 或手写校验）
	if req.Code == "" || req.Name == "" {
		response.FailWithMessage("商品编码与名称不能为空", c)
		return
	}
	if err := goodsService.CreateGoods(c.Request.Context(), req); err != nil {
		logger.WithCtx(c.Request.Context()).Mod("biz").Err(err).Error("创建商品失败")
		response.FailWithMessage(err.Error(), c)
		return
	}
	response.OkWithMessage("创建成功", c)
}
```

约定：

- 成功：`response.OkWithData(data, c)` / `response.OkWithDetailed(data, msg, c)` / `response.OkWithMessage(msg, c)`。
- 失败：`response.FailWithMessage(msg, c)`，`msg` 必须直接面向用户、可理解，不裸抛技术栈信息。
- service 返回 `error`，api 层统一转成 `FailWithMessage`；**service 层不返回 response 结构**，保持可复用。
- 业务校验失败直接返回 `errors.New("xxx")` 语义错误，由上层包装为友好文案。
- 涉及数据库约束冲突（唯一键、外键）必须捕获并翻译为友好提示，不得把驱动原始报错抛给前端。

### 1.4 GORM 使用规范

**模型定义**：所有业务表模型嵌入 `global.GVA_MODEL`，获得 `ID`、`CreatedAt`、`UpdatedAt`、`DeletedAt` 四个通用字段；自定义 `TableName()` 返回表名。

**事务**：凡涉及多表写操作（采购单+明细、销售出库+库存流水、盘点盈亏调整等），必须使用 `Transaction` 包裹，禁止"先写后补"：

```go
// 采购入库：单据状态流转 + 库存累加 + 流水记录，必须同一事务
func (s *PurchaseService) InStock(ctx context.Context, req request.InStockReq) error {
	return global.GVA_DB.Transaction(func(tx *gorm.DB) error {
		// 1. 校验并加锁单据（悲观锁，防并发重复入库）
		var order model.PurchaseOrder
		if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
			Where("id = ? AND status = ?", req.ID, model.StatusAudited).First(&order).Error; err != nil {
			return errors.New("采购单不存在或不在待入库状态")
		}
		// 2. 明细逐行入库
		for _, item := range order.Items {
			if err := tx.Model(&model.Stock{}).
				Where("sku_id = ? AND warehouse_id = ?", item.SKUId, order.WarehouseID).
				UpdateColumn("quantity", gorm.Expr("quantity + ?", item.Quantity)).Error; err != nil {
				return err
			}
			// 3. 写库存流水
			if err := tx.Create(&model.StockLog{...}).Error; err != nil {
				return err
			}
		}
		// 4. 更新单据状态
		return tx.Model(&order).Update("status", model.StatusInstock).Error
	})
}
```

**软删除**：`GVA_MODEL` 自带 `DeletedAt gorm.DeletedAt`，`Delete` 自动转为 `deleted_at` 置值；查询自动过滤已删记录（`Unscoped` 仅限审计/恢复场景，需显式说明理由）。**物理删除一律禁止**，历史单据必须保留。

**预加载**：列表/详情查询用 `Preload` 一次性取出关联，避免 N+1；嵌套关联最多两级，超出用 `Preload("...", ...)` 加条件：

```go
var goods model.Goods
err := global.GVA_DB.Preload("Brand").
	Preload("Category").
	Preload("SKUs", func(db *gorm.DB) *gorm.DB {
		return db.Where("status = ?", 1).Order("sort")
	}).
	First(&goods, id).Error
```

**分页查询**：复用 `model/common/request.PageInfo`（`page`/`pageSize`/`keyword`），`pageSize` 上限 100，`Paginate()` 已内置默认值与上限钳制：

```go
func (s *GoodsService) GetGoodsList(ctx context.Context, info request.PageInfo) (list []model.Goods, total int64, err error) {
	db := global.GVA_DB.Model(&model.Goods{})
	if info.Keyword != "" {
		db = db.Where("name LIKE ? OR code LIKE ?", "%"+info.Keyword+"%", "%"+info.Keyword+"%")
	}
	if err = db.Count(&total).Error; err != nil {
		return
	}
	err = db.Scopes(info.Paginate()).Find(&list).Error
	return
}
```

### 1.5 日志规范

使用 GVA 内置 Zap（`go.uber.org/zap`）。全局 logger 已由 `core/zap.go` 初始化并注入环境信息，业务代码禁止自建 logger、禁止 `fmt.Println` 输出业务信息。

推荐使用带 context 的日志助手 `server/utils/logger`，自动携带请求链路与模块标识：

```go
import "github.com/flipped-aurora/gin-vue-admin/server/utils/logger"

// 在 api / service 层
logger.WithCtx(c.Request.Context()).Mod("biz").Err(err).Error("创建商品失败")
logger.WithCtx(ctx).Mod("biz").Info("采购入库完成", zap.Uint("orderId", req.ID))
```

直接使用全局 logger 亦可，但须保持上下文一致性：

```go
global.GVA_LOG.Info("定时任务执行", zap.String("task", name))
global.GVA_LOG.Error("数据异常", zap.Error(err), zap.Uint("id", id))
```

约定：

- 级别：调试 `Debug` / 常规流程 `Info` / 可恢复异常 `Warn` / 不可恢复错误 `Error`。业务失败反馈给用户的错误以 `Error` 记录（含堆栈），正常校验不通过用 `Info`。
- 结构化字段统一 `zap.String`/`zap.Uint`/`zap.Error`，禁止拼接字符串传参。
- 日志内容不得包含密码、token 等敏感信息（密码字段模型上已配 `json:"-"`，注意不得再单独打印）。
- 入库、出库、审核、盘点完成等关键业务操作，日志中必须带单据号与操作者（`claims` 中取）。

### 1.6 注释规范

- **导出函数/方法必须有注释**：首行 `// FuncName 功能描述`，GVA 风格；HTTP 接口函数必须写 swagger 注解（`@Tags`/`@Summary`/`@Param`/`@Success`/`@Router`），保证 Swagger 文档完整。
- **结构体导出字段必须带行尾 `// 注释`**，与 `gorm:"comment:..."` 双写（DB 注释 + 代码注释），如 1.1 示例。
- 包级变量、常量按需注释；`TableName()` 方法可省略函数注释。
- 复杂业务逻辑（库存计算、换货双单流转）须在函数体内写关键步骤注释，禁止整段无注释的"魔法代码"。
- 中文注释为主，英文注释仅限框架对齐处；注释说明"为什么"而非复述"是什么"。

## 二、Vue3 前端规范

### 2.1 组件命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 组件文件名 | `PascalCase.vue`（单文件组件） | `GoodsList.vue`、`SkuForm.vue` |
| 模板中使用组件 | `kebab-case` 标签 | `<goods-list />`、`<sku-form />` |
| 组件 `name` 选项 | `PascalCase`，与文件名一致（script setup 下建议用 `defineOptions`） | `defineOptions({ name: 'GoodsList' })` |
| 组合式函数（composables） | `useXxx.js`，文件内导出一个函数 | `useStockWarning.js` |
| Pinia store | `useXxxStore.js` | `useGoodsStore.js` |
| 常量/枚举 | `UPPER_SNAKE_CASE`，统一收敛在 `src/utils/const.js` 或模块内 | `ORDER_STATUS = { PENDING: 1, ... }` |
| props / emit / 变量 | `camelCase`，props 类型必须显式声明 | `:page-size` → `pageSize` |

模板示例：

```vue
<template>
  <div class="goods-list">
    <el-table :data="tableData" v-loading="loading">
      <el-table-column prop="name" label="商品名称" min-width="160" />
      <el-table-column prop="code" label="商品编码" width="120" />
    </el-table>
    <el-pagination
      v-model:current-page="page"
      v-model:page-size="pageSize"
      :total="total"
      layout="total, prev, pager, next"
      @current-change="getList"
    />
  </div>
</template>
```

### 2.2 Composition API 使用规范

统一使用 `<script setup>` 语法 + Composition API，**禁止**新代码使用 Options API（`data()/methods:`）。

```vue
<script setup>
import { onMounted, ref } from 'vue'
import { ElMessage } from 'element-plus'
import { getGoodsList, deleteGoods } from '@/api/jxc/goods'

defineOptions({ name: 'GoodsList' })

const props = defineProps({
  categoryId: { type: Number, default: 0 }
})
const emit = defineEmits(['refresh'])

const tableData = ref([])
const loading = ref(false)
const page = ref(1)
const pageSize = ref(10)
const total = ref(0)

const getList = async () => {
  loading.value = true
  try {
    const res = await getGoodsList({ page: page.value, pageSize: pageSize.value, keyword: keyword.value })
    tableData.value = res.data.list
    total.value = res.data.total
  } finally {
    loading.value = false
  }
}

const handleDelete = async (row) => {
  await deleteGoods(row.id)
  ElMessage.success('删除成功')
  getList()
}

onMounted(getList)
</script>
```

约定：

- 状态用 `ref`/`reactive`，组合逻辑提取为 `composables/useXxx.js`，页面组件保持薄。
- `async/await` + `try/finally` 管理 loading；错误提示统一走 `ElMessage`（axios 拦截器已统一弹错误，页面内可不再重复）。
- 依赖 GVA 的用户信息、字典等全局能力时，复用框架 hooks（`useUserInfo`、`useDict` 等），不重复造轮子。
- 计算属性/侦听器用于派生状态与副作用，禁止在模板里写复杂表达式。

### 2.3 目录规范

`web/src/` 各目录职责分明，前端新增进销存业务统一按 `jxc` 组织：

```
web/src/
├── api/jxc/                  # 接口层：按模块一个文件，只做请求封装
│   ├── goods.js
│   ├── purchase.js
│   ├── sale.js
│   ├── stock.js
│   └── check.js
├── view/jxc/                 # 页面层：按业务模块建目录，一个路由一个页面组件
│   ├── goods/                #   GoodsList.vue / GoodsDetail.vue / SkuForm.vue
│   ├── purchase/             #   PurchaseOrderList.vue / PurchaseOrderForm.vue
│   ├── sale/                 #   SaleOrderList.vue / SaleOrderForm.vue
│   ├── stock/                #   StockList.vue / StockLogList.vue
│   └── check/                #   CheckOrderList.vue / CheckOrderForm.vue
├── pinia/                    # 全局状态：useGoodsStore.js 等，仅放跨页面共享状态
├── components/               # 公共组件：PascalCase 命名，放复用组件（ExcelUpload.vue 等）
├── composables/              # 组合式函数：useStockWarning.js 等
├── router/                   # 路由配置（动态菜单由后端下发的 component 路径驱动）
└── utils/                    # 工具函数与常量
```

接口封装模板（`web/src/api/jxc/goods.js`）：

```js
import service from '@/utils/request'

// 分页获取商品列表
export const getGoodsList = (params) =>
  service({ url: '/jxc/goods/list', method: 'get', params })

// 创建商品
export const createGoods = (data) =>
  service({ url: '/jxc/goods', method: 'post', data })

// 修改商品
export const updateGoods = (id, data) =>
  service({ url: `/jxc/goods/${id}`, method: 'put', data })
```

约定：

- **api 目录只做请求封装**，不做业务逻辑；页面只调 api，不直接写 `axios`。
- 业务页面对应菜单通过 GVA 菜单管理动态注册（component 填 `view/jxc/goods/index.vue`），页面组件放在对应模块目录，路径与菜单 component 一致。
- `components/` 只放真正跨页面复用的组件；模块内私有子组件放模块目录下。

### 2.4 样式规范

- 组件样式默认 `scoped`，避免污染全局；业务组件样式写在 `<style scoped lang="scss">` 中。
- 布局与间距优先使用 UnoCSS 原子类（本项目已启用 `@unocss/preset-wind3`）：`flex`、`items-center`、`gap-4`、`mt-2`、`text-sm`、`w-full` 等。
- 主题色、字体等全局变量走框架 `src/style` / CSS 变量，禁止在业务组件里硬编码品牌色值。
- 覆盖 Element Plus 组件样式时，在 scoped 块中用 `:deep()` 限定范围：

```vue
<style scoped lang="scss">
.goods-table {
  :deep(.el-table__header th) {
    background: var(--gva-table-header-bg, #f5f7fa);
  }
}
</style>
```

- 一律使用语义化类名（`kebab-case`）或 UnoCSS 原子类，禁止无意义缩写、禁止行内 `style` 写布局。
- 公共样式/主题覆盖放入 `src/style/`，不要在 `App.vue` 或 `main.js` 里堆积全局 CSS。

## 三、API 接口规范

### 3.1 RESTful 风格

进销存业务接口统一挂在 `/api/jxc/` 前缀下，路径用名词（复数/单数保持一致，本系统统一单数资源），HTTP 方法表达动作：

| 方法 | 路径 | 语义 |
|------|------|------|
| `GET` | `/api/jxc/goods/list` | 分页列表（查询条件走 query） |
| `GET` | `/api/jxc/goods/:id` | 单条详情 |
| `POST` | `/api/jxc/goods` | 创建 |
| `PUT` | `/api/jxc/goods/:id` | 修改 |
| `DELETE` | `/api/jxc/goods/:id` | 删除（软删除） |
| `PUT` | `/api/jxc/goods/:id/shelves` | 状态/动作类操作，动词放 URL 尾部 |
| `POST` | `/api/jxc/purchase/order/:id/audit` | 动作类接口用 `POST + 动词`，不用 `PUT` 表达动作 |
| `POST` | `/api/jxc/goods/import` | 导入（特殊资源动作） |
| `GET` | `/api/jxc/goods/export` | 导出 |

约定：

- 动作类（审核、入库、出库、取消、确认、完成）用 `POST /资源/:id/动作`；`PUT /:id` 只做资源字段修改。
- 列表一律 `/list` 显式后缀（避免与详情 `/:id` 冲突），详情用 `/:id`。
- 子资源归属用嵌套路径表达，如 `/api/jxc/sku/goods/:goodsId`。
- 路由前缀与权限点（Casbin `api`）按 `jxc/xxx` 前缀登记，权限校验由框架中间件完成。

### 3.2 请求参数命名

- 统一 `camelCase`（JSON body 与 query 均如此），后端通过 `json`/`form` tag 绑定。
- 分页参数固定为 `page`、`pageSize`（必选约定），查询关键字 `keyword`。
- 时间范围参数统一 `camelCase`：`startTime`、`endTime`。
- ID 参数 `:id` 为数字主键；跨资源 ID 用全名（`supplierId`、`warehouseId`、`orderId`）。
- 布尔/枚举字段语义化：状态用 `status`（数字枚举），是/否用 `1/0`，不在参数名里带 `is_` 前缀（数据库层除外）。

```http
GET /api/jxc/goods/list?keyword=T恤&categoryId=2&brandId=1&status=1&page=1&pageSize=10&startTime=2026-05-01&endTime=2026-05-31
```

### 3.3 响应格式统一

所有接口返回 GVA 标准结构 `{ code, data, msg }`，HTTP 状态码统一 200（认证失败 401 除外，由中间件触发）：

```json
// 成功（code=0）
{
  "code": 0,
  "data": {
    "list": [],
    "total": 0
  },
  "msg": "成功"
}

// 失败（code=7）
{
  "code": 7,
  "data": {},
  "msg": "库存不足，无法出库"
}
```

前端 `web/src/utils/request.js` 已按 `code === 0` 判定成功、`code === 7` 统一弹 `msg`，**后端不要擅自改变结构**。

### 3.4 分页格式统一

分页请求参数与响应 `data` 结构全局统一：

```json
// 请求
{
  "page": 1,
  "pageSize": 10,
  "keyword": "可选"
}

// 响应 data
{
  "list": [ /* 当前页数据 */ ],
  "total": 123
}
```

后端实现统一复用 `model/common/request.PageInfo`（内含 `Paginate()`，`pageSize` 上限 100，缺省 10），禁止各模块各自手写分页逻辑、禁止返回非 `{list,total}` 的分页结构。

## 四、Git 规范

### 4.1 分支策略

采用 `main → develop → feature/xxx` 三级模型：

```
main                # 生产分支，只接受 release 合并，可随时发布
  └── develop       # 集成分支（默认开发基线），所有 feature 合入此处
        ├── feature/jxc-goods          # 新功能：进销存商品模块
        ├── feature/jxc-purchase       # 新功能：采购模块
        ├── fix/jxc-stock-warning      # Bug 修复
        ├── docs/06-开发规范           # 文档类分支
        └── ...
```

约定：

- 禁止直接在 `main`/`develop` 上提交代码；所有人从 `develop` 切 `feature/xxx`（或 `fix/xxx`、`docs/xxx`）分支开发。
- 分支名 `kebab-case`，用 `类型/简短描述`，描述用英文或拼音，对应业务模块（`jxc-goods` 等）。
- 功能完成、自测通过后提 PR/MR 合并回 `develop`；`develop` 验证通过后，按发布计划合入 `main` 打 tag（如 `v0.1.0`）。
- 分支只负责"一件事"，一个 PR 解决一个可独立交付的问题。

### 4.2 Commit 规范

采用 **Conventional Commits** 格式：

```
<type>(<scope>): <subject>

<可选 body>
```

`type` 取值（与仓库约定一致）：

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档（含本规范、设计文档） |
| `style` | 格式调整（不影响逻辑） |
| `refactor` | 重构（不新增功能、不修 Bug） |
| `test` | 测试相关 |
| `chore` | 构建、依赖、配置等杂项 |

`scope` 为可选模块名（`jxc-goods`、`jxc-purchase`、`web`、`server`、`docs`）。

示例：

```
feat(jxc-goods): 商品列表支持分类多选筛选
fix(jxc-stock): 修复采购入库库存重复累加问题
docs: 补充 06-开发规范
refactor(jxc-sale): 抽取库存扣减公共方法
test(jxc-stock): 增加盘点差异计算用例
```

约定：

- `subject` 用中文，动词开头，一句讲清"做了什么"，不超过 50 字符；必要时 `body` 说明"为什么"。
- 一个 commit 只包含一个逻辑变更；`feat` 与 `fix` 不混在一个 commit。
- 禁止提交构建产物、本地配置、`.env` 等敏感/无关文件（参考仓库 `.gitignore`）。

### 4.3 PR/MR 流程与代码审查清单

流程：

```
feature/xxx ──PR/MR──▶ develop ──(验证)──▶ main
```

1. 开发自测：本地 `go build ./...`、`npm run lint` 通过，接口用 Swagger 联调。
2. 提 PR/MR：标题用 `<type>(<scope>): <subject>`；描述写明改动内容、测试情况、涉及接口/表变更。
3. 至少 1 名协作者 Review 通过后合并；合入前需解决全部评论与冲突。
4. 合并后删除 feature 分支；如引入表结构变化，同步更新 `docs/03-数据库设计.md` 与接口文档。

**代码审查清单**：

后端：

- [ ] 分层是否正确（router/api/service/model 各司其职，无越层）
- [ ] 所有导出函数有注释；接口有 swagger 注解
- [ ] 响应统一用 `response.Ok*/Fail*`，无裸 `c.JSON`
- [ ] 多表写操作是否在事务中；是否有并发安全（行锁/乐观锁）
- [ ] 是否使用软删除；删除操作是否检查了引用
- [ ] 金额/数量是否用 `decimal`/`int`，未用浮点
- [ ] 日志是否记录关键操作与错误（含 context、结构字段）
- [ ] 查询是否合理使用索引/预加载，无 N+1
- [ ] 敏感字段未泄漏（`json:"-"`、密码不打日志）

前端：

- [ ] 组件命名 PascalCase、模板 kebab-case；`<script setup>` 语法
- [ ] 接口封装在 `api/`，页面无裸 axios
- [ ] 样式 scoped，合理使用 UnoCSS 原子类，无硬编码主题色
- [ ] 错误提示、loading 管理完整，无未捕获异常
- [ ] 分页/响应结构符合本文档统一格式

## 五、数据库规范

### 5.1 表命名

- 全部小写、下划线分隔（`snake_case`），**业务表统一单数**（本系统约定），GVA 自带系统表（`sys_*` 复数）保持原样不动。
- 进销存业务表名直接使用业务名词，不带 `jxc_` 前缀（模块前缀体现在接口路径 `/api/jxc/`），避免表名过长。
- 主从表关系用 `_order` / `_item` 区分；日志类表 `_log`；多对多关联表 `_relation`。

| 表名 | 说明 |
|------|------|
| `goods_category` | 商品分类 |
| `brand` | 品牌 |
| `goods` | 商品 SPU |
| `goods_sku` | 商品 SKU |
| `supplier` / `customer` / `warehouse` | 供应商 / 客户 / 仓库 |
| `purchase_order` / `purchase_item` | 采购单 / 采购明细 |
| `sale_order` / `sale_item` | 销售单 / 销售明细 |
| `stock` / `stock_log` | 库存 / 库存流水 |
| `stock_check` / `stock_check_item` | 盘点单 / 盘点明细 |

### 5.2 字段命名

- 全部 `snake_case`；字段类型约定见下（对齐 `docs/03-数据库设计.md`）：

| 类别 | 类型 | 说明 |
|------|------|------|
| 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT` | GORM 主键，模型嵌入 `GVA_MODEL` |
| 时间戳 | `created_at` / `updated_at` / `deleted_at` | 由 `GVA_MODEL` 自动生成，软删除依赖 `deleted_at` |
| 金额 | `DECIMAL(12,2)` | 采购价、销售价、金额合计，禁止 `FLOAT/DOUBLE` |
| 数量 | `INT` 默认 `0` | 库存、数量 |
| 状态 | `TINYINT` | 枚举值每表定义并注释 |
| 编码 | `VARCHAR(50)` + 唯一索引 | 单据号、编码类字段 |
| 引擎/字符集 | InnoDB / utf8mb4 | 全局统一 |

- 外键字段用 `xxx_id`（`category_id`、`sku_id`、`order_id`）；布尔字段用 `TINYINT(1)`。
- 每个字段在 GORM tag 中必须带 `comment:`（生成表注释），代码行尾同步 `// 注释`。

### 5.3 索引命名

| 索引类型 | 前缀 | 示例 |
|----------|------|------|
| 唯一索引 | `uk_` + 字段名 | `uk_code`、`uk_sku_code` |
| 普通索引 | `idx_` + 字段名（多个用 `_` 连接） | `idx_parent_id`、`idx_order_no` |
| 主键 | `PRIMARY`（框架自动） | — |

GORM tag 写法（与命名规则对应）：

```go
Code string `gorm:"size:50;uniqueIndex:uk_code;comment:分类编码"`     // 唯一索引 uk_code
ParentID uint `gorm:"index:idx_parent_id;comment:父分类ID"`          // 普通索引 idx_parent_id
OrderNo string `gorm:"size:50;index:idx_order_no;comment:单据号"`    // 普通索引 idx_order_no
```

约定：

- 组合索引按查询条件顺序声明，如 `index:idx_sku_warehouse,priority:1`/`priority:2`。
- 频繁作为查询条件的字段（`status`、`warehouse_id`、`sku_id`、时间范围）必须建索引；低区分度字段（如仅两个值的 `status`）谨慎单独建索引。
- 删除/修改必须走索引定位；全表扫描出现在业务 SQL 中视为审查不通过。

### 5.4 迁移管理（GORM AutoMigrate）

- 进销存业务表在 `server/initialize/` 的初始化流程中注册，通过 GORM `AutoMigrate` 自动建表/增量同步字段，**禁止手写 SQL 建表脚本**维护业务表。
- 模型注册位置与方式（示例）：

```go
// server/initialize/ensure_tables.go 内追加进销存模型
db.AutoMigrate(
	&model.Goods{},
	&model.GoodsSKU{},
	&model.PurchaseOrder{},
	&model.PurchaseOrderItem{},
	&model.Stock{},
	&model.StockLog{},
	// ...
)
```

约定：

- 新增/修改表结构时，同步修改模型与 `docs/03-数据库设计.md`，并在 PR 描述中说明迁移影响。
- `AutoMigrate` 只增不改删：**禁止删除字段**（历史数据依赖），废弃字段保留并注释或单独走下线流程。
- 大数据量表结构变更（加索引、改类型）不在 AutoMigrate 自动执行，需评审后单独写迁移脚本并记录在 `docs/09-开发日志.md`。
- 存量数据清洗、历史数据修正禁止在业务接口里做，走一次性脚本 + 操作记录。
