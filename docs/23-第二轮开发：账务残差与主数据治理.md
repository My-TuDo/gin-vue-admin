## 一、账务：分位残差

### 问题

金额是 `decimal(14,2)`，单价也是 `decimal(12,2)`。出库成本按移动加权平均算出来再四舍五入到分：

- 3 件 / 100.00 的库存，出库行单价只能是 `33.33`，金额是 `-100.00`；
- 按“单价 × 数量”红冲，只回来 `99.99`，永久留 1 分；
- 同样，原单 3 件 100.00 分三次退货，每次按 `33.33` 回补，合计 `99.99`。

### 修复

- `internal/ledger.Position.ApplyAmount(qty, amount)`：按**精确金额**增减，校验金额方向与数量方向一致、
  不允许把数量/金额冲成负数、数量归零时金额必须归零。
- 红冲：从被冲销的 `stock_move` 行读取 `amount`，按精确金额反向（不再用 `unit_cost × qty`）。
- 退货：
  - `sale_return_item.cost_amount` 记录本行实际回补的精确成本；
  - 不是最后一次退货时按“该 SKU 原单总成本 / 原单总数量”的均价回补；
  - 最后一次退货把“原单总成本 − 已退成本”的余额全部放在最后一行，吸收残差；
  - 账本行金额用 `AmountOverride` 精确入账，`UnitCost` 只作展示/参考。

### 回归测试

- `internal/ledger`：`TestApplyAmount_ExactReversal`、`TestApplyAmount_Guards`
- `service/jxc`：`TestReversal_ExactAmountNoResidual`、`TestReturn_FinalReturnAbsorbsResidual`

## 二、盘点：并发建单唯一

### 问题

`StockCheck.Create` 原来是“先 count 进行中的盘点单，再 insert”。两个并发请求都读到 0，
就会各建一张，后续两次盘点互相覆盖。

### 修复

在同一事务里先 `SELECT ... FOR UPDATE` 锁住仓库行，再 count + insert。
同一仓库的建单请求被串行化，后到者一定看得到先到者已提交的盘点单。

为什么不用“条件唯一索引”：MySQL 没有 partial unique index；用生成列 + 唯一索引也可行，
但会引入一个只为约束存在的新列。仓库行锁最简、与 `Ledger.Post` 的锁顺序一致，不增加死锁路径。

### 回归测试

- `TestStockCheck_ConcurrentCreateOnlyOne`：4 个并发的建单请求只能成功 1 个。

## 三、主数据：DTO + Service + 编辑/停用

### 问题

- API handler 直接 `ShouldBindJSON` 到 model 并写库：客户端可以带 `ID` / `status` / 时间字段
  （mass assignment），也能绕过分层（`Router -> API -> Service -> Model`）。
- 商品 / 规格 / 仓库 / 往来单位只能新建，不能改价、改名、停用。销售单价固定取 SKU 售价后，
  **没有改价入口**，只能改库。

### 修复

- 新增 `model/jxc/request/master.go`：只接收业务允许修改的字段。
- 新增 `model/jxc/response/master.go`：`GoodsWithSkus` 作为 Service / API 共用返回类型。
- 新增 `service/jxc/master_service.go`：列表、创建、编辑、启停全部收口；校验编码唯一、
  规格条码唯一、颜色+尺码不重复、状态只能是 0/1、金额非负。
- API 只做解析 → 调 Service → 统一响应；Swagger 注释同步补齐。
- 新增接口：
  - `PUT /jxc/master/warehouses/:id`、`POST /jxc/master/warehouses/:id/status`
  - `PUT /jxc/master/goods/:id`、`POST /jxc/master/goods/:id/status`
  - `POST /jxc/master/skus/:id/status`
  - `PUT /jxc/master/partners/:id`、`POST /jxc/master/partners/:id/status`
- 列表接口新增 `active=1`：开单/补货只看启用项；基础资料页不带参数，能看到并重新启用停用项。
- 前端基础资料页：商品/往来单位/仓库都补了“编辑”“停用/启用”；
  商品编辑弹窗可改规格售价、参考进价与规格启停；已有规格不能删除（历史账本引用）。
- 销售/补货页只加载启用中的仓库、商品、规格、供应商。

### 契约变化

1. 主数据创建/更新入参不再接收 `ID` / `status` / 时间字段（状态走独立的 `/status` 接口）。
2. `GET /jxc/master/{warehouses,goods,skus,partners}` 支持 `active=1`。
3. 停用规格后，`POST /jxc/sale` 会拒绝（“SKU 已停用”）；停用商品会从 `active=1` 的商品列表消失。
4. 删除仍不提供：历史单据和账本行引用主数据，只能停用。

### 回归测试

- `TestMaster_WarehouseCRUDAndStatus`
- `TestMaster_GoodsCreateUpdateAndSkuStatus`
- `TestMaster_PartnerCRUDAndStatus`
- `TestMaster_DisabledSkuCannotSell`

## 四、数据库变更

| 变更 | 说明 |
|---|---|
| `sale_return_item.cost_amount` `decimal(14,2) default 0` | 本行实际回补成本；老数据用 `qty × unit_cost` 兜底 |

本轮**没有新增表**。字段由 `AutoMigrate` 加列；老数据的 `cost_amount` 为 0 时，
`returnedCost` 会回退到 `qty × unit_cost`，不会把历史已退成本算成 0。

权限矩阵同步从 158 条增加到 **179 条**（888/9001 各 46，9002 44，9003 23，8881 20）。
升级后必须重新执行 `docs/sql/jxc-casbin.sql` 并重启后端，否则新接口会 403。
