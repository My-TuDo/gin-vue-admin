> 适用系统：服装进销存系统（JXC，基于 Gin-Vue-Admin / GVA 框架）
>
> 关联文档：02-系统设计、03-数据库设计、04-接口设计、05-前端设计
>
> 测试范围：后端 Service/API 层（Go）、前端组件/表单（Vue3）、端到端流程（v2 规划）

## 一、测试策略

### 1.1 测试金字塔与分层策略

| 层级 | 技术栈 | 测试对象 | 执行位置 | 运行频率 |
|------|--------|----------|----------|----------|
| **单元测试** | Go `testing` + `testify` | Service 业务逻辑、Model 数据操作、工具函数 | 后端（`server/`） | 每次提交 / CI |
| **单元测试** | Vue3 `vitest` | 组件、Composables、Pinia Store、工具函数 | 前端（`web/`） | 每次提交 / CI |
| **集成测试** | Go `httptest` + 真实测试库 | API 层 + Service + Model 全链路 | 后端（`server/`） | 每次提交 / CI |
| **E2E 测试** | Playwright（v2 规划） | 核心业务流程端到端（登录 → 建单 → 出入库） | 独立环境 | 发版前 / 每日夜间 |

**原则**：

- 单元测试追求**快**（毫秒级）、隔离（不依赖真实数据库），聚焦业务规则与分支；
- 集成测试追求**真**（使用独立测试库、真实 HTTP 请求），覆盖 API → Service → 数据库全链路与事务一致性；
- 核心业务流程（采购、销售、退货、换货、盘点、出入库）以**集成测试为主**，因为库存变更是跨表事务操作，单测无法完整验证。

### 1.2 覆盖率目标

| 模块/层级 | 行覆盖率目标 | 分支覆盖率要求 | 说明 |
|-----------|:------------:|:--------------:|------|
| Service 层核心业务（purchase / sale / stock / check） | **≥ 85%** | 关键分支（库存不足、状态非法、防超卖）必须覆盖 | 业务正确性核心 |
| Model/DAO 层 | ≥ 75% | 条件查询分支 | |
| API 层（参数校验、错误响应） | ≥ 70% | 参数错误路径 | 正常 + 异常路径成对覆盖 |
| 前端核心组件（SkuSelector、单据表单、状态标签） | ≥ 60% | 校验拦截分支 | 组件级 |
| 工具函数 / 通用逻辑 | ≥ 70% | - | |

> CI 门槛：后端整体覆盖率 **< 70% 时构建失败**；核心业务模块覆盖率 **< 85% 时告警**。

### 1.3 测试环境与数据隔离

| 项目 | 约定 |
|------|------|
| 开发/生产库 | `jxc`（禁止测试写入） |
| 测试库 | `jxc_test`（独立 MySQL 实例或同一实例独立 database，由 `config.test.yaml` / 环境变量指定） |
| 测试库初始化 | 测试启动前执行 GORM AutoMigrate（或 SQL 迁移脚本），与生产迁移保持一致 |
| 数据清理 | **每个测试用例前后清理**：`setUp` 插入前置数据，`tearDown` 清空相关业务表，避免用例间相互污染 |
| 并发测试 | 测试库表使用 InnoDB + 真实事务，确保并发防超卖用例可复现 |

> 单元测试（纯逻辑）不得访问数据库；集成测试统一走 `httptest` + 测试库。

### 1.4 Mock 策略

| 依赖类型 | Mock 方式 | 说明 |
|----------|-----------|------|
| 第三方服务（短信、OSS、支付、AI 插件） | `mockgen` 生成接口 Mock / `testify/mock` | 业务层不依赖真实第三方 |
| 时间 | 依赖注入时钟（`clock` 接口）或 `time.Now()` 包装函数 | 便于断言 `order_no` 日期段、流水时间 |
| 当前登录用户 | JWT 中间件测试辅助函数生成固定身份 | 集成测试断言 `operator` 字段 |
| 数据库 | **不 Mock**：集成测试使用真实测试库 + 事务 | 库存、流水是核心资产，Mock 数据库会掩盖事务/并发缺陷 |
| 权限（Casbin） | 集成测试预置角色权限数据，或直接放行权限中间件 + 单独测权限 | 权限用例单独一组 |

## 二、后端测试规范

### 2.1 目录与命名

```
server/
├── service/jxc/
│   ├── purchase_test.go        # 采购业务单测
│   ├── sale_test.go            # 销售业务单测
│   ├── stock_test.go           # 库存业务单测
│   └── check_test.go           # 盘点业务单测
├── api/v1/jxc/
│   ├── purchase_api_test.go    # 采购 API 集成测试
│   ├── sale_api_test.go        # 销售 API 集成测试
│   ├── stock_api_test.go       # 库存 API 集成测试
│   └── check_api_test.go       # 盘点 API 集成测试
└── test/                       # 测试基础设施
    ├── db.go                   # 测试库连接、迁移、清理工具
    ├── auth.go                 # JWT 测试身份辅助函数
    └── router.go               # 组装测试用 Gin 引擎
```

| 规则 | 说明 |
|------|------|
| 文件命名 | 一律 `xxx_test.go`（与待测文件同包或 `_test` 包） |
| 函数命名 | `Test{模块}_{场景}`，如 `TestPurchaseOrder_Create_StockLock` |
| 测试库 | 独立 `jxc_test`，`setUp` / `tearDown` 保证用例隔离 |
| 数据构造 | 使用工厂函数（`testutil.NewSupplier(t, db)`）创建前置数据 |
| 表清理顺序 | 先清流水/明细（`stock_log`、`purchase_item`、`sale_item`、`stock_check_item`），再清单据/库存（`stock`、`purchase_order`、`sale_order`、`stock_check`），最后清基础资料，避免外键/软删除干扰 |

### 2.2 测试数据库约定

```go
// test/db.go 示例
func SetupTestDB(t *testing.T) *gorm.DB {
    t.Helper()
    db := testutil.NewTestDB() // 连接 jxc_test
    // 每个用例开始前：truncate 业务表（见 2.1 清理顺序）
    CleanTables(db)
    return db
}
```

1. 测试库名 `jxc_test`，由 CI 或 `make test` 自动创建并迁移；
2. 每个用例独立 `t.Run`，`t.Cleanup` 中清表；
3. 集成测试断言后必须**校验流水**（`stock_log` 的 before/change/after 三元组），这是库存正确性的关键证据；
4. 测试数据使用固定 ID 段（如供应商 ID 100+、SKU ID 200+），避免与递增序列冲突。

### 2.3 Mock 策略（后端）

| 场景 | 做法 |
|------|------|
| 第三方调用 | 接口注入 Mock（`mockgen` / `testify/mock`），断言调用参数与次数 |
| 登录身份 | 中间件测试辅助函数注入 `claims`（固定用户 `admin` / 仓管 `keeper`） |
| 编码生成 | 注入固定日期，断言 `PO-20260601-001` 这类格式 |
| 事务失败注入 | 对 Mock 的 DAO 返回错误，验证 Service 整体回滚 |

## 三、核心业务流程测试用例（重点）

> 用例编号规则：`PU` 采购、`SA` 销售、`RT` 退货、`EX` 换货、`CK` 盘点、`DS` 直接出入库、`DEL` 删除保护。
>
> 状态约定：采购单 1 待审核 / 2 已审核 / 3 已入库 / 4 已取消；销售单 1 待出库 / 2 已出库 / 3 已取消；盘点单 1 盘点中 / 2 已完成。
>
> 涉及 `stock.quantity`（现有库存）、`stock.lock_quantity`（锁定库存），`可用库存 = quantity - lock_quantity`。

### 3.1 采购入库流程

| 用例编号 | 测试场景 | 前置条件(Given) | 操作(When) | 预期结果(Then) |
|----------|----------|------------------|------------|----------------|
| PU-001 | 创建采购单（正常） | 存在供应商(100)、仓库(1)、SKU(200)；登录身份：采购员 | 调用 `POST /api/jxc/purchase/order`，提交 supplier_id=100、warehouse_id=1，明细 2 条（SKU200×100 件、单价 20；SKU201×30 件、单价 28） | 返回 code=0；采购单状态=1（待审核）；`order_no` 自动生成 `PO-YYYYMMDD-001`；`total_amount=2840.00`；明细 2 条落库 |
| PU-002 | 创建采购单（明细为空） | 同 PU-001 | 提交 `items=[]` | code≠0，提示「至少包含一条采购明细」；无单据生成 |
| PU-003 | 创建采购单（数量非法） | 同 PU-001 | 明细中 `qty=0` 或负数 | code≠0，参数校验失败；无单据生成 |
| PU-004 | 创建采购单（供应商不存在/停用） | 供应商 ID 不存在 | 提交 supplier_id=999 | code≠0，提示「供应商不存在」；无单据生成 |
| PU-005 | 审核通过 | 存在待审核采购单（状态=1） | 调用 `POST /api/jxc/purchase/order/:id/audit`，`approve=true` | code=0；状态 1→2（已审核）；可执行入库 |
| PU-006 | 审核驳回 | 存在待审核采购单（状态=1） | 调用 audit，`approve=false` | code=0；状态保持 1（待审核），可修改后重新提交；审核意见记录到操作日志 |
| PU-007 | 审核状态非法 | 采购单已入库（状态=3）或已取消（状态=4） | 调用 audit | code≠0，提示「当前状态不允许审核」；状态不变 |
| PU-008 | 采购入库（正常） | 采购单已审核（状态=2），SKU200 当前库存 0、SKU201 当前库存 0 | 调用 `POST /api/jxc/purchase/order/:id/in-stock` | code=0；状态 2→3（已入库）；SKU200 `quantity 0→100`、SKU201 `quantity 0→30`；生成 2 条流水 `business_type=purchase_in`、`business_no=采购单号`，before/change/after 正确；操作日志记录 |
| PU-009 | 采购入库（状态非法） | 采购单待审核（状态=1） | 调用 in-stock | code≠0，提示「仅已审核采购单可入库」；库存与流水均无变化 |
| PU-010 | 重复入库 | 采购单已入库（状态=3），库存已增加 | 再次调用 in-stock | code≠0，提示「该采购单已入库，禁止重复入库」；库存不变、不新增流水 |
| PU-011 | 采购入库部分 SKU 失败回滚 | 已审核采购单含 2 个 SKU，第二个 SKU 已被软删除 | 调用 in-stock | code≠0；第一个 SKU 的库存与流水**不生效**（整体回滚）；采购单状态仍为 2 |
| PU-012 | 取消采购单 | 采购单待审核或已审核 | 调用 `POST /api/jxc/purchase/order/:id/cancel` | code=0；状态→4（已取消）；库存无变化 |
| PU-013 | 取消已入库采购单 | 采购单已入库（状态=3） | 调用 cancel | code≠0，提示「已入库采购单不可取消」 |
| PU-014 | 删除待审核采购单 | 采购单待审核（状态=1），含 2 条明细 | 调用 `DELETE /api/jxc/purchase/order/:id` | code=0；单据软删除（deleted_at 记录），明细级联软删除；列表查询不返回 |
| PU-015 | 修改非待审核采购单 | 采购单已审核（状态=2） | 调用 `PUT /api/jxc/purchase/order/:id` 修改明细 | code≠0，提示「仅待审核状态可修改」；原数据不变 |

### 5.6 接口测试断言规范

| 校验维度 | 断言内容 |
|----------|----------|
| HTTP 状态码 | 401（未认证）、403（无权限）必须精确断言 |
| 业务码 | `code=0` 成功；失败场景断言 `code≠0` 且 msg 符合前端约定文案 |
| 数据副作用 | 集成测试断言**数据库实际变更**（库存 quantity/lock_quantity、流水记录、单据状态），而非仅看响应 |
| 流水一致性 | 断言 `stock_log.after_qty = before_qty + change_qty`，且业务单号可追溯 |
| 事务回滚 | 失败用例断言相关表**无任何部分写入** |
