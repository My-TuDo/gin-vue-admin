## 一、问题定性

现有实现（`stock.quantity` 可变 + `stock_log` 描述性日志）属于 **CRUD + 计数器** 模型。
它在功能上"看起来对"，但有三个结构性后果：

1. **余额与流水可以不一致，且没有任何机制能发现**。过去 8 轮修的所有库存 bug
   （丢失更新、锁量负数、收银流水 before/after 写反、盘点覆盖无视在途锁定）都不是偶然，
   而是这个模型的必然产物。
2. **没有成本。** `goods_sku.cost_price` 被"最新进价"覆盖，意味着**已卖出订单的毛利会被事后改写**。
   看板上的"毛利"不是账，是估算。
3. **单据可以被改写或抹掉。** 取消=改状态、修改=覆盖明细。于是"账上为什么是这个数"无法回答。

**设计结论**：不是给现有表加字段，而是把库存从"一个数"改成"一串事实"。
`stock` 降级为物化余额，真正的真相是一张只追加的 `stock_move`。

## 二、三个层次的分离

成熟实现都做同一件事，只是命名不同：

| 层 | 作用 | ERPNext | Odoo | 本项目 |
|---|---|---|---|---|
| 单据 | 发生了什么业务 | Purchase Receipt / Delivery Note | `stock.picking` / `stock.move` | `purchase_order` / `sale_order` |
| 账本 | 对库存与成本的影响（不可变） | **Stock Ledger Entry** | **`stock.valuation.layer`** | **`stock_move`（新）** |
| 余额 | 当前结存（可重算） | Bin | `stock.quant` | **`stock_balance`（改造 `stock`）** |

单据可以草稿、可以作废；**账本行永不可变**；余额随时能由账本重算校验。

## 三、表设计

### 3.1 `stock_move`（账本行，只追加）

```sql
CREATE TABLE stock_move (
  id              BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  warehouse_id    BIGINT UNSIGNED NOT NULL,
  sku_id          BIGINT UNSIGNED NOT NULL,
  batch_id        BIGINT UNSIGNED NULL COMMENT '批次（FIFO 时使用）',

  qty             INT NOT NULL COMMENT '有符号：入库为正、出库为负',
  unit_cost       DECIMAL(12,2) NOT NULL COMMENT '入库=入库单价；出库=结转成本单价(COGS)',
  amount          DECIMAL(14,2) NOT NULL COMMENT '有符号金额 = qty * unit_cost',

  source_type     VARCHAR(32) NOT NULL COMMENT 'purchase_in/sale_out/sale_return/exchange_out/exchange_in/direct_in/direct_out/check_gain/check_loss/reversal',
  source_id       BIGINT UNSIGNED NOT NULL COMMENT '来源单据ID',
  source_line_id  BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '来源单据明细ID（幂等键组成部分）',

  occurred_at     DATETIME(3) NOT NULL COMMENT '业务发生时间（不是入库时间）',
  created_at      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

  reversal_of     BIGINT UNSIGNED NULL COMMENT '若为红冲，指向被冲销的 move.id',
  operator        VARCHAR(50) NULL,

  UNIQUE KEY uk_move_idem (source_type, source_id, source_line_id),
  KEY idx_move_wh_sku_time (warehouse_id, sku_id, occurred_at, id)
) COMMENT '库存账本：只 INSERT，不 UPDATE，不 DELETE';
```

**设计要点**

- `qty` 有符号比"方向列"更好：金额、余额、汇总都能直接用 `SUM()`，不需要 `CASE WHEN direction`。
  现有 `sale_item.direction` 的那些特判（必须双向、方向不能为 0）在账本模型里根本不存在。
- `unit_cost` 必须**落在账本行上**。这一列是整个模型的灵魂：它把"当时的成本"冻结下来，
  于是历史毛利永远不会被后来的进价改写。
- `source_type + source_id + source_line_id` 是幂等键（**实现里没有把 `qty` 放进唯一键**；
  红冲/换货通过不同的 `source_type` 区分，不需要 `qty`）。POS 双击、网络重试、
  消息重投，只要来源相同就只会产生一行。这比任何 UI 层的 `saving` 守卫都可靠。
- `idx_move_wh_sku_time` 在 2026-10-27 接手审计时才补建；此前只有唯一索引，
  按仓库/SKU 查流水与对账都是全表扫描。
- `occurred_at` 与 `created_at` 分开：补录昨天的单据，业务时间在昨天，写入时间在今天。
  这和 ERPNext 的 `posting_date/posting_time` + `creation` 是同一个思路。

### 3.2 `stock_balance`（物化余额，可重算）

```sql
CREATE TABLE stock_balance (
  warehouse_id  BIGINT UNSIGNED NOT NULL,
  sku_id        BIGINT UNSIGNED NOT NULL,
  qty           INT NOT NULL DEFAULT 0 COMMENT '= SUM(stock_move.qty)',
  value         DECIMAL(14,2) NOT NULL DEFAULT 0 COMMENT '= SUM(stock_move.amount)',
  updated_at    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (warehouse_id, sku_id)
) COMMENT '物化视图：只由过账逻辑写入，禁止手工改';
```

保留这张表是为了查询性能（看板、收银台可售量都要频繁读），
但**它的每一行都必须能用一条 SQL 从 `stock_move` 重算出来**（见第五节对账）。

### 3.3 `stock_reservation`（预留，替代 `lock_quantity`）

```sql
CREATE TABLE stock_reservation (
  id            BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  warehouse_id  BIGINT UNSIGNED NOT NULL,
  sku_id        BIGINT UNSIGNED NOT NULL,
  qty           INT NOT NULL,
  source_type   VARCHAR(32) NOT NULL COMMENT 'sale_order / exchange_out ...',
  source_id     BIGINT UNSIGNED NOT NULL,
  source_line_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
  status        TINYINT NOT NULL DEFAULT 1 COMMENT '1 有效 2 已释放 3 已转出库',
  expires_at    DATETIME(3) NULL COMMENT '到期自动失效，避免僵尸预留',
  created_at    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_res (source_type, source_id, source_line_id)
) COMMENT '预留：有归属、有到期、可查询';
```

现有的 `stock.lock_quantity` 是**半成品**：只在销售建单时加、出库/取消时减，
没有归属、没有到期、盘点直接无视它。半成品比没有更危险，删掉换成这张表。

### 3.4 `accounting_period` + 快照（月结）

```sql
CREATE TABLE accounting_period (
  id            INT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  -- 注意：不能用 year_month，YEAR_MONTH 是 MySQL 保留字；实现与迁移都已用 period_month
  period_month  CHAR(7) NOT NULL COMMENT '2026-10',
  status        TINYINT NOT NULL DEFAULT 1 COMMENT '1 打开 2 已结账',
  closed_at     DATETIME(3) NULL,
  UNIQUE KEY uk_period (period_month)
);

CREATE TABLE stock_balance_snapshot (
  period_id     INT UNSIGNED NOT NULL,
  warehouse_id  BIGINT UNSIGNED NOT NULL,
  sku_id        BIGINT UNSIGNED NOT NULL,
  qty           INT NOT NULL,
  value         DECIMAL(14,2) NOT NULL,
  PRIMARY KEY (period_id, warehouse_id, sku_id)
) COMMENT '结账时冻结；之后所有人看到的"上月库存"都是这个数';
```

**为什么必须有月结**：店主要的不是"实时库存"，是"这个月赚了多少、上月底库存多少"。
没有快照，报表永远是"现在算一遍"，历史数据一多就慢，而且每次算出来可能不一样。

## 四、过账规则（唯一需要被严格定义的业务逻辑）

每一种业务事件，对账本产生什么影响，必须**逐条写死**：

| 事件 | 账本动作 | 成本取值 | 预留 |
|---|---|---|---|
| 采购单审核 | 无 | — | — |
| 采购入库 | `purchase_in` `qty=+N` | 该明细入库单价 | — |
| 销售单确认（开单） | 无 | — | `+N` 预留 |
| 销售出库 | `sale_out` `qty=-N` | **出库时按成本方法结转，写入 `unit_cost`** | 预留释放 |
| 退货入库 | `sale_return` `qty=+N` | **原单该行的 `unit_cost`（不是当前成本）** | — |
| 换货 | **拆两笔**：`sale_return`(+N, 原单成本) + `sale_out`(-M, 当前成本) | 同上 | — |
| 直接入库 | `direct_in` `qty=+N` | 手工指定的成本（必填） | — |
| 直接出库 | `direct_out` `qty=-N` | 当前成本 | — |
| 盘点差异 | `check_gain`/`check_loss` `qty=±diff` | 当前成本 | — |
| 红冲 | 反向 `qty`、复制原 `unit_cost`、`reversal_of=原行` | 同原行 | — |

> 实现核对：表里的「换货」在重写版本中**没有实现**，`exchange_out`/`exchange_in`
> 也不在 `MoveSource` 常量里。当前只支持采购、销售、退货、红冲、盘点。
>
> **三条关键规则，也是这个设计最有价值的部分：**

1. **退货必须用原单成本。** 用当前成本退，等于用今天进的货价，去改写上个月的毛利。
   这是通用进销存最常见的账务错误，也是"月底算不清"的头号原因。
2. **换货拆成两笔账本移动。** 一张单、两个方向的做法，把"退货入库+退款"和"销售出库+收款"
   揉成一个聚合，导致报表没法拆、毛利算不清、还要写一堆特判。拆开之后，两者各自可审计。
3. **盘点也要走账本，不能覆盖余额。** 现有实现是
   `UPDATE stock SET quantity = actual`，直接改余额。账本模型里盘点是
   `diff = 实际 - 账面` 的一条 `check_gain/check_loss` 移动，**余额永远由账本推出来**。

## 五、不变量与对账（可执行的正确性）

这是整套设计的价值所在：**正确性不是靠 code review，而是靠可执行的断言**。

```sql
-- 不变量 1：余额数量必须等于账本累加
SELECT b.warehouse_id, b.sku_id, b.qty AS balance_qty,
       COALESCE(SUM(m.qty),0) AS ledger_qty,
       b.qty - COALESCE(SUM(m.qty),0) AS diff
FROM stock_balance b
LEFT JOIN stock_move m ON m.warehouse_id=b.warehouse_id AND m.sku_id=b.sku_id
GROUP BY b.warehouse_id, b.sku_id
HAVING diff <> 0;

-- 不变量 2：余额金额必须等于账本累加
SELECT b.warehouse_id, b.sku_id, b.value, COALESCE(SUM(m.amount),0) AS ledger_value
FROM stock_balance b
LEFT JOIN stock_move m ON m.warehouse_id=b.warehouse_id AND m.sku_id=b.sku_id
GROUP BY b.warehouse_id, b.sku_id
HAVING b.value <> ledger_value;

-- 不变量 3：可用量不得为负（可售 = 余额 - 有效预留）
SELECT b.*, COALESCE(SUM(r.qty),0) AS reserved
FROM stock_balance b
LEFT JOIN stock_reservation r
  ON r.warehouse_id=b.warehouse_id AND r.sku_id=b.sku_id AND r.status=1
GROUP BY b.warehouse_id, b.sku_id
HAVING b.qty - reserved < 0;
```

这三条查询应该：
1. 被写成 Go 测试（`TestLedgerInvariants`），每次改动过账逻辑都跑；
2. 被做成一个「一键对账」页面（经营运维视角：商家能自己按一下，知道账实是否相符）；
3. 在 CI 里对测试库跑一遍。

> 实现核对：第 3 条**没有做到**。`.github/workflows/ci.yaml` 没有 MySQL service，
> `service/jxc` 的集成测试在 CI 里只会 `t.Skip`。这是一条设计愿望，不是已实现事实。

ERPNext 的做法可以对照：[它有一个专门的 `Stock Ledger Invariant Check` 报表](https://raw.githubusercontent.com/frappe/erpnext/29ff0ce286255307ac78652776a8e158b89222ae/erpnext/stock/report/stock_ledger_invariant_check/stock_ledger_invariant_check.py)，
把"逐行累加"和"库里存的余额"逐行对比，还允许一键生成 `Repost Item Valuation` 重算。这说明
**成熟产品也承认余额会漂移**，区别是它们有检测和修复手段，而我们现在没有。

## 六、成本方法：先选移动加权平均，但把边界留出来

服装业两种主流做法：

| 方法 | 优点 | 代价 |
|---|---|---|
| **移动加权平均** | 一张表、一个 `avg_cost`，实现简单；符合多数小微企业会计习惯 | 无法回答"这批货赚了多少" |
| **FIFO（批次层）** | 能算每批毛利，季末清仓时特别有用 | 需要 `stock_layer` + 出库时逐层消耗，逻辑复杂度明显上升 |

**决策：v1 用移动加权平均**，因为目标店的诉求是"这个月赚了多少"，不是"这批货赚了多少"。
但账本模型本身把成本方法**隔离在过账逻辑内部**：`stock_move.unit_cost` 是入参/出参，
换算法不需要动表结构。将来要 FIFO，只需新增 `stock_layer` 并在过账时改一段消耗逻辑，
单据、余额、报表全部不变。

> 这是这个设计里最像"架构师"的一次取舍：**不在第一天选最复杂的方案，而是让选择可替换。**

## 七、禁止跨期回填（用约束消灭一整类问题）

允许任意补录历史单据，会让"历史成本被改写"成为常态，于是需要"重过账（repost）"这种重型机制
（ERPNext 的 `Repost Item Valuation` 就是为此存在，且它会把账本行改掉——与"不可变"矛盾）。

**本设计的取舍：允许当期补录，禁止跨期回填。**

- 过账时校验：`occurred_at` 所属期间必须是 `status=打开`；
- 已结账期间的数据要更正 → 只能在当期开红冲单，冲掉影响、在当期体现；
- 好处：账本永远不需要被改写，`repost` 这类机制**根本不需要存在**。

代价是"上月忘了录，这月补进本月"，会计上不完美，但对一个单店系统是可接受的简化——
而它换来的"账本永不可变"要在文档里明说，不能装作没有代价。

## 八、与现有代码的映射（迁移视角）

> 实现核对：这一节描述的是**从旧 `stock` 表迁移**的方案；`rewrite/jxc-v3` 实际是新建
> `erp_v3` 库、没有执行这段迁移，也不存在“53 张历史销售单”的数据。不要把本节当成
> 当前库的表结构说明。

| 现有 | 变成 | 处理方式 |
|---|---|---|
| `stock`（含 `lock_quantity`） | `stock_balance` | 保留表名/字段，只由过账写入；`lock_quantity` 删除 |
| `stock_log` | `stock_move` | 补 `amount/unit_cost/source_line_id/idempotency/reversal_of`；历史数据回填 `unit_cost=0` 并标记 `legacy=1` |
| `sale_item.direction` | 删除 | 换货拆成两张单据，`sale_out`/`sale_return` 各记一笔 |
| `sale_order.order_type=3`（换货） | 保留为"业务单" | 但内部生成两条账本移动，不再是一单两方向 |
| `goods_sku.cost_price` | 保留 | 降级为"参考进价"（开单时提示用），**不再作为毛利依据** |
| 看板毛利 | `SUM(sale_item.amount) - SUM(sale_move.amount WHERE source_type='sale_out')` | 从账本算，不再用 cost_price 估 |
| `sale_order.status` | `draft → posted → reversed` | posted 后明细不可改；取消=开红冲单 |

**历史数据怎么办**：53 张历史销售单没有成本信息，无法凭空还原。
方案是回填 `unit_cost = 0` 并打 `legacy` 标记，看板对 legacy 期间单独标注
「该期间无成本数据」。**这是诚实的做法**——假装历史毛利准确，比承认没有更糟。

## 九、这个设计对"作品集"意味着什么

面试时"我写了一个进销存"几乎没有区分度。但有区分度的是能讲清这些：

1. **余额不是真相。** 为什么库存系统必须有账本，为什么"一个 quantity 字段 + 一个日志表"不够。
2. **不变量比事务更重要。** 事务保证一次操作的原子性，不变量保证**一万次操作之后账还是对的**。
3. **成本必须冻结在发生的那一刻。** 为什么退货要用原单成本，为什么 cost_price 不能拿来算历史毛利。
4. **不可变单据的代价与收益。** 收益是永远可审计；代价是不能改历史，所以要用冲销——
   这解释了为什么正规财务系统里"红字冲销"是标配。
5. **用约束消灭问题。** 禁止跨期回填 → 不需要 repost 机制。这是"设计消除复杂度"的典型例子。

这五点对应的是**领域建模能力**，不是框架熟练度，也不是功能数量。

## 十、这个设计对"商业产品观测台"意味着什么

写完代码只是开始，真实产品还需要（这些现在完全空白）：

| 商业产品里的东西 | 在这里对应什么 |
|---|---|
| **对账日** | 每月/每季商家要能一键核对"账实是否相符"，差异要能解释。对应第五节的三个查询做成页面 |
| **数据修复** | 出错了不能改历史，要开红冲单。需要 UI 上的"红冲"入口，和权限控制 |
| **升级** | 表结构变更必须向前兼容，因为商家的历史数据不能重建、不能停机太久。ADR-0005 的迁移脚本就是这个的雏形 |
| **支持成本** | 客户问"为什么这个数是 X"，要能一路点回到原始单据。`source_type + source_id` 就是这条链路 |
| **责任边界** | posted 之后谁都不能改，包括管理员。这是产品对客户的承诺，不是技术洁癖 |

## 十一、本文的边界（明确不做什么）

- ~~不重写前端~~ → **前端也重写**（2026-10-27 客户决定）：旧前端是"一表一页 CRUD + 弹窗"的堆砌，
  属于需要被替换的设计，不因为后端换了就保留。新前端单独做设计（信息架构 / 交互 / 视觉），
  不复用旧页面。详见 `17-前端重设计.md`。
- **不动 GVA 生态**：RBAC/菜单/代码生成继续用于主数据；但**账本核心不进代码生成器的表驱动流程**，
  理由见 ADR-0007。
- **不做 FIFO**（v1）：边界留好，但不在第一天实现。
- **不做多仓调拨、批次追踪、序列号**：超出单店范围。

## 十二、实现时踩到的两个点（记录，避免再犯）

1. **`year_month` 是 MySQL 保留关键字**（interval 单位）。把它用作列名、并在原生 `WHERE` 里裸写，
   直接语法错误，导致所有过账失败。已改名 `period_month`。教训：会计期间这类字段命名，先查关键字表。
2. **单价精度必须和金额精度一致**。设计初稿把 `unit_cost` 定成 `decimal(12,4)`，
   但金额用"分"，四舍五入只到 2 位——留 4 位只是暗示一个不存在的精度。已收敛为 `decimal(12,2)`。
