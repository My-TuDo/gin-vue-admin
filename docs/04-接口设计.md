# 04-接口设计

## 一、通用约定

### 1.1 Base URL 与路由前缀

所有接口统一使用以下基础路径，由 Nginx 将 `/api` 前缀转发至后端服务：

```
Base URL: /api
```

- 开发环境：Vite 代理将 `/api` 转发到后端（如 `http://localhost:8888`）
- 生产环境：Nginx 配置 `/api` 反向代理到 Gin 服务
- 业务接口统一挂在 `/api/jxc/` 前缀下，按模块组织（goods、sku、purchase、sale、stock、check 等）

### 1.2 认证方式

采用 **Bearer JWT（JSON Web Token）** 认证，与 GVA 框架一致。

- 登录使用 GVA 自带登录接口（`POST /login`），获取 `token`
- 所有业务接口请求头必须携带：

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

| HTTP 状态码 | 说明 |
|-------------|------|
| 401 | 未登录或 token 已过期/无效 |
| 403 | 已登录但 Casbin 权限不足（无该接口权限） |

> 除登录接口外，其余接口均需登录；权限通过 Casbin 的 RBAC 体系按角色控制（见 02-系统设计-权限矩阵）。

### 1.3 统一响应格式

所有接口返回统一 JSON 结构：

```json
{
  "code": 0,
  "data": {},
  "msg": "操作成功"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | int | 0 表示成功；非 0 表示失败（GVA 默认业务错误码为 7） |
| data | object/array | 业务数据，失败时一般为 `null` 或 `{}` |
| msg | string | 提示信息，前端可直接展示 |

**示例（失败）**：

```json
{
  "code": 7,
  "data": {},
  "msg": "库存不足，无法出库"
}
```

### 1.4 分页参数

分页查询接口统一使用以下 Query 参数（对应 GVA 的 `Page` / `PageSize`）：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| page | int | 否 | 1 | 页码，从 1 开始 |
| pageSize | int | 否 | 10 | 每页条数，最大 100 |

分页响应 `data` 结构统一为：

```json
{
  "list": [],
  "total": 0,
  "page": 1,
  "pageSize": 10
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| list | array | 当前页数据 |
| total | int | 总条数 |
| page | int | 当前页码 |
| pageSize | int | 每页条数 |

### 1.5 业务状态与枚举

以下枚举与 03-数据库设计 保持一致，接口中直接使用数值：

**采购单状态（purchase_order.status）**

| 值 | 含义 | 说明 |
|----|------|------|
| 1 | 待审核 | 创建后初始状态，可修改/删除/取消 |
| 2 | 已审核（待入库） | 审核通过，可执行入库，可取消 |
| 3 | 已入库 | 已执行入库，终态 |
| 4 | 已取消 | 终态 |

**采购单状态流转**

```
待审核(1) ──审核通过──► 已审核(2) ──入库──► 已入库(3)
    │                      │
    └──────取消────────────┘
              │
              ▼
          已取消(4)
```

**销售单类型（sale_order.order_type）**

| 值 | 含义 | 说明 |
|----|------|------|
| 1 | 正常销售 | 创建时锁定库存，确认出库扣减库存 |
| 2 | 退货退款 | 关联原单（original_order_id），确认后库存增加 |
| 3 | 换货出库 | 换出商品，确认后扣减库存 |
| 4 | 换货入库 | 换入商品，确认后增加库存 |

**销售单状态（sale_order.status）**

| 值 | 含义 | 说明 |
|----|------|------|
| 1 | 待出库 | 创建后初始状态，可确认/取消/删除 |
| 2 | 已出库 | 已完成库存变更，终态 |
| 3 | 已取消 | 终态 |

> 对退货单（order_type=2）和换货入库单（order_type=4）而言，「已出库」状态表示「已完成退货/换货入库」，其语义为单据已完成。

**销售单状态流转**

```
待出库(1) ──确认（出库/退货入库）──► 已出库(2)
    │
    └────取消──► 已取消(3)
```

**盘点单状态（stock_check.status）**

| 值 | 含义 | 说明 |
|----|------|------|
| 1 | 盘点中 | 创建后初始状态，可录入明细/删除 |
| 2 | 已完成 | 差异已调整、流水已生成，终态 |

**库存流水业务类型（stock_log.business_type）**

| 值 | 含义 | 变更方向 |
|----|------|----------|
| purchase_in | 采购入库 | 正数（增加） |
| sale_out | 销售出库（含换货出库） | 负数（扣减） |
| sale_return | 销售退货/换货入库 | 正数（增加） |
| check_in | 盘点盘盈 | 正数（增加） |
| check_out | 盘点盘亏 | 负数（扣减） |
| direct_in | 直接入库 | 正数（增加） |
| direct_out | 直接出库 | 负数（扣减） |

### 1.6 数据格式约定

| 约定项 | 说明 |
|--------|------|
| 时间 | 统一返回 `2006-01-02 15:04:05`（如 `2026-06-01 10:30:00`） |
| 金额 | DECIMAL(12,2)，返回字符串或保留两位小数的数值，避免浮点误差 |
| 数量 | int，可正可负（流水 change_qty 为负表示出库） |
| 编码 | `order_no`、`code` 等业务编码由后端自动生成，创建时无需传 |
| 软删除 | 已删除记录不返回；删除操作记录 `deleted_at`，非物理删除 |

## 二、基础资料接口

### 2.1 商品分类（goods_category）

分类采用 **parent_id 自引用** 树形结构，支持无限层级。

**接口清单**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/jxc/category/tree | 分类树（不分页，全量） |
| GET | /api/jxc/category/list | 分类扁平分页列表 |
| GET | /api/jxc/category/:id | 分类详情 |
| POST | /api/jxc/category | 创建分类 |
| PUT | /api/jxc/category/:id | 修改分类 |
| DELETE | /api/jxc/category/:id | 删除分类 |
| PUT | /api/jxc/category/:id/status | 启用/停用分类 |

**① 分类树查询**

```
GET /api/jxc/category/tree
```

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| status | int | 否 | 按状态筛选：1=启用，0=停用；不传返回全部 |
| keyword | string | 否 | 按名称模糊搜索，命中节点保留其祖先链 |

响应示例：

```json
{
  "code": 0,
  "data": [
    {
      "id": 1,
      "parent_id": null,
      "code": "CAT01",
      "name": "女装",
      "sort": 1,
      "status": 1,
      "remark": "",
      "created_at": "2026-05-01 09:00:00",
      "children": [
        {
          "id": 2,
          "parent_id": 1,
          "code": "CAT0101",
          "name": "上衣",
          "sort": 1,
          "status": 1,
          "remark": "",
          "created_at": "2026-05-01 09:10:00",
          "children": []
        }
      ]
    }
  ],
  "msg": "获取成功"
}
```

业务说明：`children` 为空数组表示叶子节点；排序按 `sort` 升序。

**② 创建分类**

```
POST /api/jxc/category
```

Body：

```json
{
  "parent_id": 1,
  "code": "CAT010101",
  "name": "T恤",
  "sort": 1,
  "remark": "夏季主推"
}
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| parent_id | int | 否 | 父分类ID，空/NULL 表示一级分类 |
| code | string | 是 | 分类编码，全局唯一，创建后不可修改 |
| name | string | 是 | 分类名称 |
| sort | int | 否 | 排序值，越小越靠前，默认 0 |
| remark | string | 否 | 备注 |

响应示例：

```json
{
  "code": 0,
  "data": {
    "id": 8
  },
  "msg": "创建成功"
}
```

**③ 修改分类**

```
PUT /api/jxc/category/:id
```

Body 同创建（`code` 不可修改）；`parent_id` 不可设置为其自身或其子孙节点。

**④ 删除分类**

```
DELETE /api/jxc/category/:id
```

业务说明：
- 若该分类下存在子分类，禁止删除
- 若该分类已被商品（goods）引用，禁止删除
- 满足条件时执行软删除

**⑤ 启用/停用**

```
PUT /api/jxc/category/:id/status
```

Body：

```json
{ "status": 0 }
```

## 三、商品中心接口

### 3.1 商品 SPU（goods）

采用 **SPU + SKU** 两级模型，创建/修改商品时可同时维护其 SKU 列表。

**接口清单**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/jxc/goods/list | 商品分页列表（多条件筛选） |
| GET | /api/jxc/goods/:id | 商品详情（含 SKU 列表） |
| POST | /api/jxc/goods | 创建商品（含 SKU） |
| PUT | /api/jxc/goods/:id | 修改商品 |
| DELETE | /api/jxc/goods/:id | 删除商品 |
| PUT | /api/jxc/goods/:id/shelves | 商品上架/下架 |
| POST | /api/jxc/goods/import | Excel 导入商品 |
| GET | /api/jxc/goods/export | Excel 导出商品 |

**① 商品分页列表**

```
GET /api/jxc/goods/list?keyword=T恤&category_id=2&brand_id=1&status=1&page=1&pageSize=10
```

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|

| status | int | 否 | 状态：1=上架，0=下架 |
| page / pageSize | int | 否 | 分页参数 |

响应示例：

```json
{
  "code": 0,
  "data": {
    "list": [
      {
        "id": 1,
        "code": "SP001",
        "name": "圆领纯棉T恤",
        "category_id": 2,
        "category_name": "上衣",
        "brand_id": 1,
        "brand_name": "无品牌",
        "unit": "件",
        "image": "https://cdn.example.com/sp001.jpg",
        "status": 1,
```

## 五、销售中心接口

销售单为 **主从结构**：销售单（sale_order）+ 销售明细（sale_item）。通过 `order_type` + `original_order_id` 统一支持正常销售、退货退款、换货。

**单据类型**

| 值 | 类型 | 说明 |
|----|------|------|
| 1 | 正常销售 | 创建时锁定库存，确认出库扣减库存 |
| 2 | 退货退款 | 关联原单，确认后增加库存 |
| 3 | 换货出库 | 换出商品，确认后扣减库存 |
| 4 | 换货入库 | 换入商品，确认后增加库存 |

**状态流转**

```
待出库(1) ──确认（出库/退货入库）──► 已出库(2)
    │
    └────取消──► 已取消(3)
```

```json
{
```


| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| customer_id | int | 否 | 客户ID，可为空（匿名零售） |

业务说明（创建时锁定库存，事务内执行）：
1. 校验每个 SKU 可用库存（`quantity - lock_quantity`）充足，不足则整单拒绝
2. 锁定库存：`stock.lock_quantity += qty`
3. 创建销售单（`order_type=1`，状态=待出库）及明细
4. `total_amount` 由明细自动汇总（`Σ qty × price`）
5. `order_no` 自动生成（格式 `SO-YYYYMMDD-XXX`）

```json
{
```

| 参数 | 类型 | 必填 | 说明 |

业务说明：

- 退货明细 `qty` 为正数（入库时库存增加），不锁定库存
- 校验原单必须存在且已出库（状态=2），且退货数量不超过原单对应 SKU 的已售数量
- 确认退货后按明细执行入库，见「⑦ 确认」

```
POST /api/jxc/sale/order/exchange
```

Body：

```json
{

  "warehouse_id": 1,
  "remark": "换同款大一号",
  "out_items": [
    { "sku_id": 10, "qty": 1, "price": 59.00 }
  ],
  "in_items": [
    { "sku_id": 12, "qty": 1, "price": 59.00 }
  ]
}
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| original_order_id | int | 是 | 原销售单ID |
| customer_id | int | 否 | 客户ID |
| warehouse_id | int | 是 | 仓库ID |
| out_items | array | 是 | 换出商品明细（创建 order_type=3 换货出库单） |
| in_items | array | 是 | 换入商品明细（创建 order_type=4 换货入库单） |

业务说明：
- 一次调用生成 **两张销售单**：
  - 换货出库单：`order_type=3`，明细为 `out_items`，确认时扣减库存（锁定机制同正常销售）
  - 换货入库单：`order_type=4`，明细为 `in_items`，确认时增加库存
  - 两单均关联同一 `original_order_id`，通过原单追溯完整换货链路
- 两张单在同一事务中创建；`out_items` 对应 SKU 需校验可用库存充足

**⑥ 修改 / 删除销售单**

```
PUT /api/jxc/sale/order/:id        # 仅待出库(1)，明细整体替换
DELETE /api/jxc/sale/order/:id     # 仅待出库(1)
```

业务说明：
- 修改仅限「待出库」状态；修改明细时需重新校验可用库存并调整锁定数量
- 删除仅限「待出库」状态；删除时 **释放已锁定的库存**（`lock_quantity -= qty`），明细级联删除

**⑦ 确认出库 / 退货入库**

```
POST /api/jxc/sale/order/:id/confirm
```

Body（可空）：`{ "remark": "" }`

业务说明（事务内执行），根据 `order_type` 分支处理：

| order_type | 动作 | 库存操作 | 流水类型 |
|------------|------|----------|----------|
| 1 正常销售 | 出库 | `quantity -= qty`，`lock_quantity -= qty` | sale_out |
| 2 退货退款 | 退货入库 | `quantity += qty` | sale_return |
| 3 换货出库 | 出库 | `quantity -= qty`，`lock_quantity -= qty` | sale_out |
| 4 换货入库 | 换货入库 | `quantity += qty` | sale_return |

- 出库（type 1/3）时再次校验库存充足，扣减使用 `WHERE quantity - lock_quantity >= N` 防超卖
- 入库（type 2/4）时无库存记录自动创建
- 逐条写入库存流水：`business_no=销售单号`，记录 before/change/after
- 销售单状态 1 → 2（已出库）
- 任一明细操作失败则整体回滚

**⑧ 取消销售单**

```
POST /api/jxc/sale/order/:id/cancel
```

Body（可空）：`{ "remark": "客户取消" }`

业务说明：
- 仅「待出库(1)」状态可取消
- 若该单锁定了库存（type 1/3），取消时释放锁定：`lock_quantity -= qty`
- 状态变更为「已取消(3)」；退货/换货入库单（type 2/4）未锁定库存，直接置为已取消

Body（可空）：`{ "remark": "" }`

业务说明（事务内执行）：
1. 校验状态必须为「盘点中(1)」，且每个 SKU 均已录入 `actual_qty`（未录入视为盘亏为 0，建议前端提示）
2. 筛选 `diff_qty ≠ 0` 的明细
3. 逐条调整库存：`stock.quantity += diff_qty`（正=盘盈，负=盘亏）
4. 逐条写入库存流水：
   - `diff_qty > 0`：`business_type=check_in`（盘盈）
   - `diff_qty < 0`：`business_type=check_out`（盘亏）
   - `business_no=盘点单号`，`change_qty=diff_qty`
5. 盘点单状态 1 → 2（已完成）
6. 任一 SKU 调整失败则整体回滚

**⑥ 删除盘点单**

```
DELETE /api/jxc/check/order/:id
```

业务说明：仅「盘点中(1)」状态可删除，明细级联删除；已完成不可删除。

## 九、扫码枪接口（v2-M3 新增）

> 定位：小程序扫码 → 投递到指定收银台会话 → PC 收银台轮询并**自动加入购物车**（无人工确认，收银全程 PC 端）。
> 权限：casbin 已配（888/9001 全 6 接口、9002 业务 4 接口，见 `docs/sql/pos-permissions.sql`）。

### 9.1 会话管理（PC 收银台设置）

| 方法 | 路径 | 请求 | 响应 data | 说明 |
|------|------|------|-----------|------|
| POST | /api/jxc/pos/session | `{"remark":"1号收银机"}` | `{id, code, remark, status, createdAt}` | 生成 6 位收银台码（不混淆字符 A-Z/2-9 去 I/O/0/1，唯一索引） |
| PUT | /api/jxc/pos/session/disable | `{"code":"A2B3C4"}` | - | 作废旧码（重置）；作废后扫码/轮询立即失败，小程序需重新绑定 |
| GET | /api/jxc/pos/session/check?code=A2B3C4 | - | `{id, code, ...}` | 小程序绑定校验；无效码返回 code=7 |

### 9.2 扫码上架（小程序）

| 方法 | 路径 | 请求 | 响应 data | 说明 |
|------|------|------|-----------|------|
| POST | /api/jxc/pos/scan | `{"session":"A2B3C4","barcode":"690...","qty":1}` | `{id, session, skuId, qty, status, createdAt}` | 按条码或 skuCode 上架；qty 默认 1、上限 99；**同会话同 SKU 未消费记录数量累加**；会话无效/作废报错 |

### 9.3 PC 轮询与消费

| 方法 | 路径 | 请求 | 响应 data | 说明 |
|------|------|------|-----------|------|
| GET | /api/jxc/pos/scan/pending?session=A2B3C4 | - | `[{id, session, skuId, qty, status, createdAt, sku:{id, skuCode, goodsName, color, size, salePrice, barcode}}]` | 本会话未消费条目（status=0，FIFO）；sku 可能为 null（商品已删）；会话无效报错 |
| PUT | /api/jxc/pos/scan/confirm | `{"ids":[1,2]}` | - | 批量标记已消费（PC 自动加购后调用，幂等）；记录 handled_at |

**状态机**：`0=未消费`（小程序已扫、PC 未处理）→ `1=已消费`（PC 已自动加入购物车）。同 SKU 连续扫码在未消费态合并数量，PC 消费后新扫码重新计数。

## 十、事务与一致性约束

以下接口必须在数据库事务中执行，任一步骤失败则整体回滚（与 03-数据库设计-九 一致）：

| 接口 | 事务内容 |
|------|----------|
| POST /api/jxc/purchase/order/:id/in-stock | 更新采购单状态 + 更新 stock 多条 + 插入 stock_log 多条 |
| POST /api/jxc/sale/order/:id/confirm（出库） | 更新销售单状态 + 扣减 stock 多条 + 插入 stock_log 多条 |
| POST /api/jxc/sale/order/:id/confirm（退货/换货入库） | 更新销售单状态 + 增加 stock 多条 + 插入 stock_log 多条 |
| POST /api/jxc/check/order/:id/complete | 更新盘点单状态 + 调整 stock 多条 + 插入 stock_log 多条 |
| POST /api/jxc/stock/direct-in | 更新 stock + 插入 stock_log |
| POST /api/jxc/stock/direct-out | 扣减 stock + 插入 stock_log |
| POST /api/jxc/sale/order（正常销售/换货） | 锁定库存 + 创建销售单/明细 |
| DELETE /api/jxc/sale/order/:id（待出库） | 释放锁定库存 + 级联删除明细 |

**统一规则**：
1. 所有涉及库存变更的操作，先写 `stock_log`，再更新 `stock`，保证流水可追溯
2. 库存扣减统一使用 `WHERE quantity - lock_quantity >= N` 条件，防止并发超卖
3. 出库、盘点等操作写入流水时使用 `before_qty` / `change_qty` / `after_qty` 三元组还原变更全貌
4. 单据编码（order_no、check_no、code 等）由后端统一生成，前端不参与
