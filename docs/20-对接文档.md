## 一、项目是什么

单店（可扩多仓）服装零售的进销存：采购入库、开单出库、退货、红冲、盘点、库存台账与对账、月报与月结。

**核心设计立场**：库存不是一个数字，是一串不可变的事实（账本）。
`stock_balance` 是物化视图，任何一行的值都必须能由 `stock_move` 重算出来。
所有正确性都围绕这一条展开，读代码前先接受这个前提。

**不在范围内**：小程序、多仓调拨、批次/序列号、会员储值、促销。见 `19` 第六节。

## 二、技术栈

| 层 | 选型 | 版本 |
|---|---|---|
| 后端 | Go + Gin + GORM + MySQL | Go 1.24 / MySQL 8~9 |
| 框架 | Gin-Vue-Admin（v3.0.0） | 提供 RBAC、菜单、JWT、Casbin |
| 前端 | Vue 3 + Element Plus + Vite | vue 3.5 / element-plus 2.13 |

GVA 只负责"外壳"（登录、权限、布局、系统管理），进销存业务全部是自定义代码。
**账本核心不走 GVA 的代码生成器**——生成器的世界观是一表一 CRUD，没有"不可变事实"这个概念（见 `adr/0007`）。

## 四、数据模型

21 张表。核心是账本五表（另加 `doc_sequence` 发号表）：

| 表 | 作用 | 可变性 |
|---|---|---|
| `stock_move` | 账本行：`qty` 有符号、`unit_cost` 冻结、来源单据、幂等键 | **只 INSERT** |
| `stock_balance` | 物化余额（`warehouse_id + sku_id` 主键） | 只由过账写 |
| `stock_reservation` | 预留（有归属、可释放、可转出库） | 状态流转 |
| `accounting_period` | 会计期间（`period_month` 唯一） | 打开 → 已结账 |
| `stock_balance_snapshot` | 结账时冻结的余额 | 一次写入 |

业务表：`purchase_order/purchase_item`、`purchase_return/purchase_return_item`、
`sale_order/sale_item`、`sale_return/sale_return_item`、`stock_reversal`、
`stock_check/stock_check_item`。

主数据：`warehouse`、`goods`、`goods_sku`、`jxc_partner`（`kind` 区分供应商/客户）。

### 不变量（改代码前必须守住）

```
balance.qty   == SUM(move.qty)
balance.value == SUM(move.amount)
balance.qty - SUM(active reservation.qty) >= 0
```

三条都实现在 `internal/ledger/invariant.go`，通过 `LedgerService.Reconcile` 暴露成「一键对账」。

## 五、过账规则（唯一需要严格理解的逻辑）

`LedgerService.Post(ctx, db, moves)` 内部顺序：

1. 校验每条移动的语义（入库为正、出库为负、来源类型合法）
2. 校验业务发生月所在期间**未结账**
3. **幂等**：`(source_type, source_id, source_line_id)` 已存在则跳过
4. `SELECT ... FOR UPDATE` 锁住余额行（不存在则建 0 行）
5. 按移动方向算成本：
   - 入库：用 `MoveInput.UnitCost`，金额 = 单价 × 数量
   - 出库：用当前移动加权平均，**把成本写死在账本行上**
6. 校验可售量（`余额 - 有效预留`）不为负
7. 写 `stock_move`，更新 `stock_balance`

**三条最容易踩的业务规则：**

| 规则 | 为什么 |
|---|---|
| 退货用**原单成本**，不用当前均价 | 用今天的成本退上个月的货，等于改写上个月毛利 |
| 出库时先转出预留再记账 | 否则自己占着自己的库存，"卖光最后一件"会假失败（曾是真 bug） |
| 采购红冲前校验货没被卖掉 | 已卖出的货整单冲回会让库存变负，账就假了 |
| 红冲按**被冲销账本行的原单价**反向，不走当前均价 | 否则剩余批次成本被改写（10@5+10@7 冲第一张，旧实现会留 60 而不是 70） |
| 有退货单的销售单禁止整单红冲 | 否则退货回补一次、红冲再回补一次，库存多出来 |
| 盘点完成前核对账面数是否变化 | 否则会按过期快照调账，把盘点期间的出入库抹掉 |

## 六、接口清单

统一响应：`{"code":0,"data":...,"msg":"成功"}`，`code != 0` 即失败，`msg` 直接可展示。
鉴权：请求头 `x-token`（GVA 登录后返回）。

五个单据分页端点（`/jxc/sale/page`、`/jxc/purchase/page`、`/jxc/return/page`、
`/jxc/purchase-return/page`、`/jxc/reversal/page`）统一支持以下 query 参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `page` / `pageSize` | int | 默认 1 / 20，pageSize 上限 100 |
| `status` | int | 单据状态；红冲只有已过账（1） |

| `warehouseId` | uint | 仓库；红冲通过来源单关联 |
| `partnerId` | uint | 客户/供应商；红冲通过来源单关联 |

| `sourceType` | string | 仅红冲：`purchase` / `sale` |

## 七、开发约定

1. **分层**：handler 只做解析/调服务/响应；业务规则在 service；**库存写入只能走 `LedgerService`**。
   现状核查：`stock_balance` 的写操作只出现在 `service/jxc/ledger.go`；
   其它文件只在读（`period_service.go` 汇总金额、`stockcheck_service.go` 建单时 LEFT JOIN 账面数）。
   加代码时请保持这条边界，否则不变量会被绕过。
2. **金额**：对外用元（`float64`，2 位小数），内部计算一律用 `money.Cents`（整数分）。
3. **时间**：业务时间 `occurredAt` 与写入时间 `createdAt` 分开存；期间按 `occurredAt` 判定。
4. **错误信息**：写给用户看，要能指导下一步（"可售库存不足：结存 7，已预留 0，本次需要 9"），
   不要返回 `sql: no rows` 这类内部细节。
5. **字段命名**：DB 用 snake_case；JSON 用 camelCase；GVA 的 `GVA_MODEL.CreatedAt` 没有 json tag，
   前端读的是 `CreatedAt`（大写），这个坑踩过一次。
6. **测试**：任何涉及库存/金额的改动都要有集成测试（`service/jxc/*_test.go`，跑真 MySQL，
   无库自动 Skip）。纯算法放 `internal/ledger`，不依赖 DB。

## 九、本地运行

```bash

cd server && go build -o jxc.exe . && ./jxc.exe       # 8888
```


## 十、排查手册

| 现象 | 原因 | 处理 |
|---|---|---|
| 所有 `/jxc` 返回"权限不足" | casbin 没策略或没重启 | 灌 `docs/sql/jxc-casbin.sql` 后**重启** |
| 接口 500 空响应 | handler panic（GVA recovery 吞栈） | 看后端日志；常见是服务字段未初始化 |
| 出库提示可售不足 | 结存不够或被未出库单占用 | 看台账可售 / 查预留 |
| 采购入库后库存没变 | 只点了「审核」 | 需再点「入库」 |
| 结账报"账实不符" | 余额被直接改过 | 先对账处理差异 |
| 红冲报"该批货已卖出" | 整单冲回会变负库存 | 改用退货或盘亏 |
| 页面数据为空但接口有数据 | 前端读了 `createdAt`（实际是 `CreatedAt`） | 见第七节第 5 条 |
| 前端构建 OOM | 大依赖 | `NODE_OPTIONS=--max-old-space-size=4096` |

## 十一、已知限制

1. **没有小程序**：旧版的扫码枪投递未迁移，PC 端是唯一入口。
2. **主数据已收口，但仍没有硬删除**：仓库/商品/规格/往来单位都支持编辑与停用，
   入参改为 DTO（客户端不能再传 `ID`/`status`/时间字段做 mass assignment）；停用的规格不能开单。
   删除仍不提供：历史单据与账本行引用着它们，删掉会让账无法解释，只能停用。
3. **没有打印/导出**：小票、对账单都缺。
4. **单币种、无税**：成本按不含税金额记录，没有税额与发票概念。
5. **期间只能开不能回**：结账后没有"反结账"接口，错了只能红冲。
6. **对账已提供最近结果，但壳层尚未切换**：后端新增 `/ledger/reconcile/last` + 60s 缓存，
   手动对账仍可强制刷新；壳层目前仍调用同步 `/reconcile`，切到 `/last` 后进入 `/jxc`
   才不会触发全仓扫描。
7. **盘点“进行中唯一”已并发安全**：同一仓库建单前锁仓库行，并发只会成功一张；
   锁顺序与 `Ledger.Post` 一致。
8. **采购退货前后端已接通**：`purchase_return` 支持部分退货、按原采购单价出库，
   过账时校验库存与已退上限；单据页已有“采购退货”tab 与采购单行“退货”入口。
   采购红冲仍保留给“整单录入错误”的场景。
9. **分位残差已处理**：红冲按被冲销账本行的**精确金额**反向；退货在最后一次
   把原单剩余成本一并回补（3 件 100 元分三次退 = 33.33 + 33.33 + 33.34）。
10. **销售开单与出库仍保留两次请求，但已有原子接口**：前端目前仍先 `POST /jxc/sale` 再
    `POST /jxc/sale/:id/ship`；后端已提供 `POST /jxc/sale/checkout`（单事务），
    前端切换后即可消除“两次请求之间断网留草稿/预留”的风险。
11. **没有前端锁文件**：仓库没有 `package-lock.json`，`.gitignore` 还忽略了 `pnpm-lock.yaml`。
    CI 已新增独立的 `Backend JXC (MySQL)` job（带 MySQL 8.4 service，硬门禁），
    但全量 backend job 仍是 `continue-on-error`，待链路稳定后再收紧。
12. **冒烟/演示数据会累积**：没有删除接口，`seed-demo.py`、`e2e-smoke.py` 每次新建仓库/SKU。
13. **部分前端页面还没切到新接口**：单据页仍取前 100 条做前端筛选，工作台仍拉 5 个列表，
   壳层仍调用同步对账。后端已提供 Search / Dashboard / LastReconcile，切换清单见 `docs/27`。
